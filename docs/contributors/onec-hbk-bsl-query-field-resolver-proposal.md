# Proposal: резолвер полей текстов запросов «алиас → таблица → тип поля по метаданным»

**Статус:** MVP реализован (2026-07-22) — `analysis/query_field_resolver.py` +
`tests/test_query_field_resolver.py`: нормализация `type_info`, карта алиасов
(соединения, виртуальные таблицы, вложенные запросы), резолвер цепочек с
`ambiguous`/`candidates` для составных типов, протяжка типов полей ВТ через
пакет. Не реализовано из списка ниже: извлечение запросов из форм/СКД (п. 4),
MCP-тул поверх резолвера.
**Контекст:** прикладной сценарий — where-used реквизита: найти все места
использования конкретного реквизита конкретного объекта метаданных. Тексты
запросов — пласт, который не покрыт ни одной из веток анализа BSL-кода:
`BslTypeEngine` (см. `type-inference-specific-metadata-identity.md`)
сознательно не лезет в строковые литералы, а аннотации типов в
документирующих комментариях и межпроцедурное профилирование вызовов
работают только с процедурным кодом.

## Мотивация: по числу вхождений это весомее межпроцедурного анализа

Замер прикладного сценария (where-used реквизита `ГоловнаяОрганизация`
справочника `Организации`, ЗУП 3.1.37.54): 1679 строк с токеном в 380
XML-файлах плюс заметная доля из 5151 BSL-строки приходится на строковые
литералы текстов запросов. Формы вхождений — контекстно-зависимые цепочки:

- `УплаченныйНДФЛ.Организация.ГоловнаяОрганизация` — алиас таблицы запроса,
  разыменование через ссылочное поле;
- `Организация.ГоловнаяОрганизация` — алиас, совпадающий с именем поля
  (типичный источник путаницы для текстового поиска);
- `Список.ГоловнаяОрганизация`, `Объект.ГоловнаяОрганизация`,
  `Отбор.ГоловнаяОрганизация` — пути данных форм, где «таблица» — основная
  таблица динамического списка или тип основного реквизита формы.

При этом одноимённые реквизиты/измерения объявлены у десятков других
объектов конфигурации (Сотрудники, ПодразделенияОрганизаций, ~11 регистров
накопления, документы) — без разрешения контекста текстовое совпадение не
отличает разыменование `СправочникСсылка.Организации` от чужого
собственного поля.

## Идея механизма

Это **не** `BslTypeEngine` и не полноценный тайпчекер запросов — отдельный
небольшой резолвер идентичности полей, работающий от метаданных:

1. **Алиас → таблица.** Разбор секций `ИЗ` / `СОЕДИНЕНИЕ` (`КАК Алиас`)
   текста запроса даёт отображение алиасов на таблицы-источники
   (`Справочник.Организации`, `РегистрСведений.X.СрезПоследних`, ...).
2. **Таблица → тип поля.** По индексу метаданных конфигурации: имя поля →
   реквизит/измерение/ресурс → его тип. Для ссылочных типов
   (`СправочникСсылка.Организации`) цепочка разыменовывается дальше:
   `Алиас.Организация.ГоловнаяОрганизация` = поле `Организация` таблицы за
   алиасом (тип `СправочникСсылка.Организации`) → реквизит
   `ГоловнаяОрганизация` справочника `Организации`.
3. **Результат** — конкретная идентичность (`Справочник.Организации.Реквизит.
   ГоловнаяОрганизация`), та же цель, что у резолвинга конкретной
   идентичности в BSL-коде (`type-inference-specific-metadata-identity.md`),
   но для другого языка.

## Источники текстов запросов (все три нужны)

- **BSL-литералы** — `Запрос.Текст = "..."`, включая конкатенацию и
  `СтрШаблон`; извлечение литерала из AST уже доступно, границы того, что
  считаем «статически известным текстом», — открытый вопрос.
- **СКД / макеты** — схемы компоновки данных в XML (наборы данных с
  запросом), плюс вычисляемые поля с путями данных.
- **Формы** — динамические списки (основная таблица или произвольный
  запрос), пути данных элементов (`Список.X`, `Объект.X`, `Отбор.X`) —
  строго говоря, не тексты запросов, а пути данных, но разрешаются тем же
  шагом 2 после определения «таблицы» контекста (основная таблица списка,
  тип основного реквизита формы).

## Известные сложности (осознанно не проработано)

- Вложенные запросы и временные таблицы (`ПОМЕСТИТЬ` / использование ВТ в
  последующих запросах пакета) — поля ВТ наследуют типы из создавшего её
  запроса, нужна протяжка через пакет.
- Виртуальные таблицы (`СрезПоследних`, `Обороты`, `ОстаткиИОбороты`) —
  состав полей отличается от основной таблицы регистра.
- `ВЫРАЗИТЬ(Поле КАК Справочник.Организации)` — явное сужение типа, самый
  простой случай (тип задан прямо в тексте).
- Составные типы ссылочных полей — разыменование через поле с составным
  типом даёт множество кандидатов (аналог `ambiguous`/`candidates` из
  `bsl_callers`).
- Динамически собираемые тексты запросов (конкатенация с условиями,
  подстановка имён таблиц) — честная граница применимости; кандидат по
  токену останется, идентичность — «неизвестно».
  
## Что уже есть в кодовой базе (ревизия 2026-07-22)

Разведка показала, что бо́льшая часть фундамента существует:

- **Грамматика SDBL** — tree-sitter-грамматика языка запросов поставляется
  с tree-sitter-hbk (`_ts_bsl.sdbl_language()`,
  `analysis/document_snapshot.py`). Парсер запросов писать не нужно.
- **Извлечение запросов из BSL-литералов** — `_build_query_text_blocks` +
  `_parse_sdbl_query_text` (`document_snapshot.py`); на этом уже работает
  семейство диагностик query_text/query_metadata/query_runtime.
- **Хелперы «алиас → источник»** — `analysis/sdbl_cst.py`:
  `query_source_uses` (включая виртуальные таблицы и соединения),
  `source_alias_name`, `dotted_identifier_parts`, `query_temp_table_names`;
  плюс готовое отображение корней таблиц ru/en → вид метаданных в
  `diagnostic/rules/query_metadata_rules.py`. Правила BSL174/187/236/238
  уже сверяют источники запросов с метаданными в бою.
- **Индекс метаданных с типами полей** — SQLite `meta_objects` /
  `meta_members` с неусечённым `type_info` (вида `cfg:CatalogRef.Организации`;
  реквизиты, измерения/ресурсы регистров, реквизиты ТЧ) —
  `indexer/symbol_index.py`, `indexer/metadata_parser.py`; наружу — MCP-тул
  `bsl_meta_object`. Это и есть индекс «объект → поля → типы».
- **Смежное (парсинг типовых аннотаций комментариев):** документирующие
  комментарии уже извлекаются целиком (`doc_comment`,
  `analysis/symbols.py`) и лежат в индексе символов; не хватает только
  структурного парсинга секций `Параметры:` / `Возвращаемое значение:` в
  типы.

Реальный объём новой работы сжимается до:

1. единый резолвер цепочки `Алиас.Поле.Поле2` поверх существующих хелперов
   (сейчас каждое правило использует их по-своему);
2. нормализация токенов `type_info`
   (`cfg:CatalogRef.Организации` → `Справочник.Организации`; составные
   типы — разбор списка токенов);
3. протяжка типов полей временных таблиц через пакет запросов (имена ВТ
   уже находятся, типы полей — нет);
4. извлечение запросов/основных таблиц из форм (динамические списки) и
   схем СКД — XML форм правила уже читают (BSL274), но не для типизации.

## Что не входит

- Полная проверка типов / валидация запросов — цель только идентичность
  полей для where-used.
- Права, РЛС, настройки СКД пользователя — другие источники, другой вопрос.
