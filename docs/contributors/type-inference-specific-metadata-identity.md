**Статус:** реализовано (`src/onec_hbk_bsl/analysis/type_inference.py`,
`src/onec_hbk_bsl/lsp/server.py:_cached_type_engine`), покрыто тестами
(`tests/test_lsp_server.py::TestInferSpecificMetadataIdentity`, 13 тестов
по мотивам разобранных реальных примеров). `ruff check` чисто, полный
`pytest` — 1551 passed (было 1538 + 13 новых), 0 регрессий, 29
предсуществующих провалов не тронуты (`mcp`/`setuptools_scm` отсутствуют в
окружении). OACS (`acs`) недоступен в этом окружении — фиксация только в
этом документе, без `acs checkpoint`/evidence.

**Одно отклонение от пункта 4 при реализации**: `ИЛИ`-цепочка сужает,
только если род (`Kind`) **одинаков** у всех дизъюнктов (не "одинаков или
разный", как было написано ниже изначально) — чтобы не усложнять модель
данных TypeScope до множества пар `(kind, name)`, а обойтись парой
`(kind, {names})`. Все реальные `ИЛИ`-цепочки, встреченные при проверке,
и так были одного рода, так что это не теряет покрытие на практике.

**Контекст:** побочная находка при анализе задачи построения графа обращений
к конкретным реквизитам объектов метаданных — при попытке понять, кто
обращается к `<выражение>.ИНН`, где `<выражение>` — ссылка именно на
Организацию. Связанный баг обхода цепочки (`_resolve_call` не спускался
рекурсивно по `access`) уже исправлен отдельно, но исправление сознательно
ограничено родовым типом (`СправочникСсылка`/`ДокументОбъект`) — конкретное
имя объекта не сохраняется. Эта задача — следующий шаг поверх того фикса.

## Зачем это вообще нужно (переформулировка цели `type_inference.py`)

`type_inference.py` в этом контексте нужен **исключительно** для одной вещи:
понять, что переменная — это ссылка/объект конкретного объекта метаданных
(`СправочникСсылка.Организации`, `ДокументОбъект.ПереносОтпуска`), чтобы потом
можно было искать обращения к её конкретным реквизитам. Родовые платформенные
типы (`Запрос` → `РезультатЗапроса` → `ТаблицаЗначений`, `HTTPОтвет`,
`Структура` и т.п.) для этой цели не нужны вообще — они существуют в
`RETURN_TYPE_MAP` ради другого потребителя (`server.py`: hover/completion в
LSP) и не должны расширяться ради этой задачи (см. отдельное обсуждение —
дальнейший рост `RETURN_TYPE_MAP` "про запас" признан не имеющим смысла).

## Текущее состояние (что уже есть и чего не хватает)

`_flatten_chain` уже разбирает `Справочники.Организации.НайтиПоКоду(...)` в
шаги `[("id","Справочники"), ("prop","Организации"), ("call","НайтиПоКоду")]`
— конкретное имя `"Организации"` физически присутствует в `steps[1]`. Но
`_resolve_access_chain` его тут же отбрасывает:

```python
global_type = _GLOBAL_MANAGER_TYPES.get(base_name.casefold())
if global_type and len(steps) > 1 and steps[1][0] == "prop":
    current_type = global_type          # "СправочникМенеджер" — родовой тип,
    remaining = steps[2:]               # "Организации" потеряно
```

Дальше `current_type` эволюционирует только через родовые ключи
`RETURN_TYPE_MAP` (`"справочникменеджер.найтипокоду"` → `"СправочникСсылка"`)
— на выходе `engine.infer(...)` возвращает `"СправочникСсылка"`, а не
`"СправочникСсылка.Организации"`.

## Предлагаемое изменение (зафиксировано)

Ключевой ограничитель: резолвинг в `BslTypeEngine` происходит **один раз**,
при обходе AST в конструкторе (`_walk`), а не лениво по запросу — значит
"нести специфичное имя" должно жить в данных, которые сохраняются в
`TypeScope`, а не быть параметром самого `infer()` (там уже нечего выбирать,
если в scope лежит одна голая строка).

1. **`TypeScope`** хранит на каждую переменную пару
   `(generic_type: str, specific_name: str | None)` вместо одной строки —
   вычисляется за тот же единственный проход `_walk`, второго прохода не
   нужно. `set(name, type_name, specific_name=None)`; `get(name)` возвращает
   только `generic_type` (не меняется для существующих потребителей);
   `get_full(name)` возвращает пару.
2. **`BslTypeEngine.infer(var_name, line0, metadata_only: bool = False)`** —
   новый опциональный параметр.
   - `metadata_only=False` (по умолчанию) — **побайтово** как сейчас:
     возвращает `generic_type`. Это обязательно, потому что `server.py:1218`
     дергает `_engine.infer(name, line)` двухаргументно для hover в LSP,
     причём для любых цепочек, не только метаданных (`Запрос.Выполнить()
     .Выгрузить()` → `"ТаблицаЗначений"`, `HTTPСоединение.Получить()` →
     `"HTTPОтвет"` и т.п.) — это регрессировать нельзя.
   - `metadata_only=True` — возвращает `f"{generic_type}.{specific_name}"`
     когда `specific_name` известен, иначе `None` ("Неопределено"). Новый
     потребитель (граф метаданных), существующих вызовов нет.
3. В `_resolve_access_chain`, когда `global_type` найден и `steps[1]` —
   `("prop", "Организации")`, инициализировать пару
   `(current_type, specific_name) = ("СправочникМенеджер", "Организации")`.
   На каждом шаге `remaining` резолвить `current_type` через
   `RETURN_TYPE_MAP` как сейчас (ключ строится из родового типа —
   `RETURN_TYPE_MAP` не меняется и не должен знать о конкретных именах);
   `specific_name` пронести без изменений через все хопы, но **обнулить**,
   как только `current_type` стал `""` (резолвинг сорвался) — специфичное
   имя не должно "висеть" на неизвестном типе.
4. Формат составной строки (`"СправочникСсылка.Организации"`) совпадает с
   тем, как сам 1С называет ссылочные типы (`Тип("СправочникСсылка
   .Организации")`) — не изобретаем новую нотацию.

## Открытый вопрос: перенос через промежуточную переменную — ЗАКРЫТ

`Мен = Справочники.Организации; Эл = Мен.НайтиПоКоду(1);` — двухшаговая форма
той же идиомы. Проверено против реального дерева (`BslParser`, не по
комментарию-грамматике): `Справочники.Организации` без вызова парсится в
узел `property_access` — `property_access(access(identifier"Справочники") .
property"Организации")`. `_resolve_expr` сегодня не имеет ветки для
`property_access` вообще (только `new_expression`/`call_expression`/
`identifier`/`expression`), поэтому это присваивание сейчас молча
резолвится в `""` — предположение "пара в TypeScope решит это само собой"
было неверным без явного изменения `_resolve_expr`.

Решение — **не** узкий спецкейс ("только 2 шага, только глобальная
коллекция"), а переиспользование существующей рекурсии:

```python
elif ct == "property_access":
    return self._resolve_access_chain(child, scope)
```

`_flatten_chain` уже трактует `access`/`identifier`/`property`/
`method_call` одинаково независимо от типа внешнего узла (`call_expression`
или `property_access`) — `property_access`-узел для `Справочники.Организации`
структурно идентичен первому сегменту `call_expression`. Проверено вручную
на дереве: `Мен` получает пару `("СправочникМенеджер", "Организации")`,
`Эл = Мен.НайтиПоКоду(1)` подхватывает её из `scope.get_full("Мен")` и
резолвит дальше через `RETURN_TYPE_MAP` без изменений в `_resolve_access_chain`.

Это не risky-обобщение: в предыдущем фиксе (тот самый, что чинил обход
цепочки) `property_access`-резолвинг был прототипирован и работал —
откачен только ради scope-дисциплины того фикса ("узкая цель — почини
рекурсию"), не из-за технической проблемы.
Общий (не только "глобальная коллекция + имя") резолвинг `property_access`
через `RETURN_TYPE_MAP` — согласованное следствие, не scope creep: сам
`RETURN_TYPE_MAP` уже трактует свойства и методы одинаково (см. комментарий
в `_resolve_access_chain` про `деревозначений.строки`).

## Проверка на реальном коде

Дизайн (до реализации) прогонялся вручную против нескольких образцов
реального прикладного кода на 1С (конфигурация типа "1С:Зарплата и
управление персоналом" с прикладным расширением) — источники не
приводятся дословно (пути и имена конкретных объектов конфигурации
опущены), важны только структурные находки.

Первый образец — общий серверный модуль, создающий бизнес-процесс по
заявке сотрудника. Честный результат — большинство присваиваний в этом
модуле не резолвятся (обращение к элементу коллекции по индексу-переменной
— тип неизвестен в принципе статически; записи в реквизиты объекта — LHS
`property_access`, типы объектов не отслеживаются, только переменные — это
ожидаемо и соответствует цели). Но всплыли два реальных, устранимых
пробела — добавлены в scope:

### 2. `RETURN_TYPE_MAP`: `ПустаяСсылка`/`EmptyRef`

В реальном коде встречается конструкция `Справочники.Пользователи.ПустаяСсылка()`.
Цепочка резолвится до `("СправочникМенеджер", "Пользователи")`, но ключа
`"справочникменеджер.пустаяссылка"` в таблице нет — резолвинг рвётся, хотя
`ПустаяСсылка()` — один из самых частых методов менеджеров (Ссылка того же
рода). Это не «рост RETURN_TYPE_MAP про запас» (который отклонён) — это
родовое звено Менеджер→Ссылка того же семейства, что уже есть для
`Найти`/`НайтиПоКоду`/`НайтиПоНаименованию`. Добавить только для менеджеров,
которые уже присутствуют в таблице (симметрично существующему покрытию, не
расширяя на непроверенные роды):

```python
"справочникменеджер.пустаяссылка": "СправочникСсылка",
"catalogmanager.emptyref": "СправочникСсылка",
"документменеджер.пустаяссылка": "ДокументСсылка",
"documentmanager.emptyref": "DocumentRef",
"перечислениеменеджер.пустаяссылка": "ПеречислениеСсылка",
```

(`"ДокументСсылка"` как тип-строка нигде раньше не встречалась в таблице —
только `"документссылка.получитьобъект"` как ключ, так что термин уже
согласован с существующим написанием, просто раньше не было записи с ним
как со *значением*.)

**Ещё один экземпляр того же пробела** найден в другом реальном общем
модуле:

```
Организация = Справочники.Организации.Выбрать();
Пока Организация.Следующий() Цикл
    Результат.Добавить(Организация.Ссылка);
КонецЦикла;
```

`Выбрать()` — ещё один универсальный метод менеджера (курсор выборки),
которого нет в таблице (`"результатзапроса.выбрать"` есть, но это другой
базовый тип — `РезультатЗапроса`, не менеджер). Добавить курсорный тип и
его `.Ссылка`:

```python
"справочникменеджер.выбрать": "СправочникВыборка",
"catalogmanager.select": "CatalogSelection",
"документменеджер.выбрать": "ДокументВыборка",
"documentmanager.select": "DocumentSelection",
"справочниквыборка.ссылка": "СправочникСсылка",
"catalogselection.ref": "CatalogRef",
"документвыборка.ссылка": "ДокументСсылка",
"documentselection.ref": "DocumentRef",
```

С этими записями `Организация.Ссылка` резолвится в `"СправочникСсылка
.Организации"` **бесплатно** — `specific_name` из пункта 1 протаскивается
через оба хопа (`Выбрать` и `.Ссылка`) без дополнительного кода, раз оба
резолвятся успешно.

### 3. Значения перечислений (`Перечисления.Имя.Значение`)

В том же реальном коде встречается конструкция
`Перечисления.ВариантыВажностиЗадачи.Обычная`. Структурно не такой, как
цепочка справочника: третий сегмент для справочника/документа — это метод
из конечного, перечислимого множества (живёт в `RETURN_TYPE_MAP`); третий
сегмент перечисления — это **конкретное значение**, их бесконечно много, в
таблицу не занесёшь. Резолвинг через `RETURN_TYPE_MAP` здесь принципиально
не подходит.

Фикс — специальный (self-limiting) кейс в цикле `_resolve_access_chain`:
как только `current_type` — это ещё сырой `ПеречислениеМенеджер`/
`EnumManager` (т.е. это первый шаг сразу после `_GLOBAL_MANAGER_TYPES`,
до всякого похода в `RETURN_TYPE_MAP`) и следующий шаг — `prop` (не
`call` — обращение к значению перечисления всегда без скобок), то это
валидный доступ к значению независимо от его имени:

```python
_ENUM_MANAGER_TYPES = {"перечислениеменеджер", "enummanager"}
...
for kind, name in remaining:
    if kind == "prop" and specific_name and current_type.casefold() in _ENUM_MANAGER_TYPES:
        current_type = "ПеречислениеСсылка"
        continue
    if kind in ("call", "prop") and current_type:
        key = f"{current_type.casefold()}.{name.casefold()}"
        current_type = self._rtm.get(key, "")
    else:
        current_type = ""
    if not current_type:
        specific_name = None
```

Условие само себя ограничивает: после первого срабатывания `current_type`
уже не равен `ПеречислениеМенеджер`/`EnumManager`, повторно не сработает.
`specific_name` остаётся неизменным — имя конкретного значения сознательно
не входит в идентичность, только имя типа перечисления.

### 4. Type narrowing через `Если ТипЗнч(Х) = Тип("Kind.Name") Тогда`

В том же модуле встречается: `Организация = ПравилоОбработкиЗаявки
.Подразделение.Источник;` (нерезолвится — динамическая цепочка через
переменную цикла) — но следующая строка `Если ТипЗнч(Организация) =
Тип("СправочникСсылка.ПодразделенияОрганизаций") Тогда` явно говорит
конкретный тип `Организация` внутри `Тогда`-ветки. В прикладном коде на 1С
(особенно в решениях на базе БСП) это частый идиом компенсации отсутствия
статической типизации — потенциально заметно увеличивает покрытие цели
задачи там, где прямой AST-инференс присваивания бессилен.

Проверено против реального дерева (`BslParser`):

```
if_statement
  IF_KEYWORD
  expression → binary_expression
    expression → method_call(identifier"ТипЗнч", arguments(expression→identifier"Организация"))
    operator "="
    expression → method_call(identifier"Тип", arguments(expression→const_expression→string→string_content:"Kind.Name"))
  THEN_KEYWORD
  <тело Тогда-ветки как прямые дети if_statement>
  elseif_clause*  (ELSIF_KEYWORD, expression, THEN_KEYWORD, <тело>)
  else_clause?    (ELSE_KEYWORD, <тело>)
  ENDIF_KEYWORD
```

`Тип(...)`/`ТипЗнч(...)` — голый `method_call` без `access`/`call_expression`
(не то, что сейчас понимает `_resolve_expr`).

**Дизайн:**

- `_walk` получает спецкейс для `if_statement` (сейчас его нет вообще — тело
  веток обходится с тем же `scope`, что и снаружи, т.к. в BSL нет блочной
  области видимости). Для `Тогда`-ветки и каждого `elseif_clause`: если
  условие матчится на паттерн ниже, создаётся **дочерний** `TypeScope` с
  единственной сужающей записью, тело ветки обходится с ним; иначе — тело
  обходится с тем же родительским `scope` (без сужения).
- `scope_at_line` обобщается: сейчас берёт первое совпадение диапазона
  (годится, пока диапазоны — только процедуры, они не вложены). С
  branch-scope диапазоны вкладываются друг в друга — нужно выбирать
  **наименьший подходящий диапазон** (вложенный побеждает объемлющий), а не
  первый найденный.
- Матчер паттерна (сознательно только эта точная форма, в обе стороны
  операндов `=`): `binary_expression` c operator `"="`, один операнд —
  `method_call` с identifier `ТипЗнч`/`TypeOf` и единственным
  аргументом-`identifier`, другой — `method_call` с identifier `Тип`/`Type`
  и единственным аргументом — строковый литерал вида `"Kind.Name"`.
- `Иначе`/`ИначеЕсли` без совпавшего паттерна не получают сужения (мы знаем
  только, чем Х **не является**, не чем является) — тело обходится с
  родительским `scope` без изменений.
- Скобки вокруг условия, `ТипЗнч` от не-`identifier` выражения — любая
  форма условия за пределами описанных паттернов просто не даёт сужения
  (безопасный fallback = текущее поведение, не регрессия).

**Расширение: `ИЛИ`-цепочки одного рода (подтверждено на реальном коде).**

В другом реальном общем модуле встретилась функция, вычисляющая список
организаций по ссылке на произвольный объект — вся она построена на этом
паттерне, и **больше половины** её веток — не одиночное равенство, а
цепочка через `ИЛИ`:

```
ИначеЕсли ТипЗнч(Ссылка) = Тип("ДокументСсылка.А")
    ИЛИ ТипЗнч(Ссылка) = Тип("ДокументСсылка.Б")
    ИЛИ ТипЗнч(Ссылка) = Тип("ДокументСсылка.В")
Тогда
    Результат.Добавить(Ссылка.Организация);
```

Проверено против дерева: `ИЛИ`-цепочка — это левоассоциативная вложенность
`binary_expression` с `operator: "ИЛИ"`, где каждый лист — свой
`binary_expression` с `operator: "="` (та же форма, что для одиночного
равенства). Без поддержки этого паттерна пункт 4 покрыл бы меньшинство
веток именно в том виде, в каком идиома реально используется.

Во всех цепочках этого модуля род (`ДокументСсылка`/`СправочникСсылка`/
`БизнесПроцессСсылка`) **одинаков** у всех дизъюнктов — различается только
конкретное имя. Дизайн:

- Извлечение условия обобщается: рекурсивно разворачивать
  `binary_expression` с `operator: "ИЛИ"` на оба операнда, собирая плоский
  список листьев; каждый лист должен матчиться на одиночный паттерн
  `ТипЗнч(Х) = Тип("Kind.Name")` (в обе стороны операндов, как и раньше).
- Сужение применяется **только если**: (а) переменная `Х` одна и та же во
  всех листьях, (б) все листья успешно распарсились (ни один не выпал из
  паттерна — иначе никакого сужения вообще, all-or-nothing, без частичных
  результатов). Род (`Kind`) может быть одинаковым (частый случай на
  практике) или разным — в обоих случаях сужение допустимо, просто
  specific-часть становится множеством пар, а не одной парой.
- `TypeScope` соответственно хранит специфичную часть не как
  `str | None`, а как `frozenset[tuple[str, str]] | None` — множество пар
  `(kind, name)` вместо одной. Для пунктов 1-3 (единственная ветка) это
  всегда множество из одного элемента — не меняет их поведение, просто
  обобщённое представление.
- `infer(var, line, metadata_only=True)` возвращает: `None`, если множество
  пусто/неизвестно; одиночную строку `"Kind.Name"`, если в множестве ровно
  один элемент (как в пунктах 1-3, никакой видимой разницы для простого
  случая); отсортированный `list[str]` (`["ДокументСсылка.А",
  "ДокументСсылка.Б", ...]"`), если элементов больше одного. Новый
  потребитель обязан быть готов и к строке, и к списку.
- `ИЛИ`-цепочка, где хотя бы один лист не матчится на паттерн (например,
  `ТипЗнч(Х) = Тип(...) ИЛИ Y = 1`), не даёт сужения вообще — не
  вычисляем частичное множество из тех листьев, что распознались.

### 5. Неявные контекстные переменные модуля объекта (`Ссылка`/`ЭтотОбъект`)

Найдено в модуле объекта одного из справочников (реальный прикладной код)
— `Ссылка` (и `ЭтотОбъект`) нигде в теле модуля не присваивается и не
объявляется: это переменные, которые платформа подставляет в модуль
объекта справочника/документа неявно (в найденном примере `Ссылка`
передавалась аргументом в вызов серверной интеграционной процедуры). Их
тип определяется не содержимым AST-тела, а **тем, каким модулем является
файл** (`Catalogs/<Имя>/Ext/ObjectModule.bsl`) — принципиально другой
источник информации, чем пункты 1-4.

**Архитектурное решение (обсуждено отдельно): парсер (`BslParser`/`Tree`) не
трогаем.** `parse_content` возвращает либо настоящий tree-sitter `Tree`
(C-расширение, на который нельзя вешать произвольные атрибуты), либо
`_RegexTree` — в обоих случаях смешивать "синтаксис" и "чей это модуль" в
одном объекте означало бы либо технически не работающее, либо
несогласованное между двумя режимами решение. Докстринг `parse_content`
и так уже явно ограничивает роль `file_path` — "used for error messages
only" (`bsl_parser.py:105`) — это осознанная граница. Вся кодовая база уже
последовательно использует отдельную, path-based функцию для владельца
модуля (`config_helpers.current_module_xml_context(path)` +
`metadata_registry.collection_for_alias`), не трогая парсер — этим же
паттерном пользуются `query_metadata_rules.py`, `module_structure_rules.py`
и другие diagnostic-правила уже сейчас.

**Дизайн:** `BslTypeEngine.__init__` получает новый опциональный параметр
`module_path: str | None = None`. Использует уже существующую
инфраструктуру, ничего не изобретая:

```python
_OBJECT_MODULE_SUFFIX = "Объект"   # ObjectModule.bsl: Ссылка + ЭтотОбъект
_RECORDSET_MODULE_SUFFIX = "НаборЗаписей"  # RecordSetModule.bsl: только ЭтотОбъект

def _seed_implicit_module_vars(self, module_path: str) -> None:
    basename = Path(module_path).name.casefold()
    if basename == "objectmodule.bsl":
        obj_suffix, has_ref = _OBJECT_MODULE_SUFFIX, True
    elif basename == "recordsetmodule.bsl":
        obj_suffix, has_ref = _RECORDSET_MODULE_SUFFIX, False
    else:
        return  # см. ограничение scope ниже
    ctx = current_module_xml_context(module_path)
    folder, object_name = ctx.get("folder"), ctx.get("object_name")
    if not folder or not object_name:
        return
    collection_ru = collection_for_alias(folder.casefold())
    generic = _GLOBAL_MANAGER_TYPES.get((collection_ru or "").casefold())
    if not generic or "Менеджер" not in generic:
        return
    if has_ref:
        self._module_scope.set("Ссылка", generic.replace("Менеджер", "Ссылка"), object_name)
    self._module_scope.set("ЭтотОбъект", generic.replace("Менеджер", obj_suffix), object_name)
```

`server.py:2685` (`_cached_type_engine`) передаёт `module_path=_uri_to_path(uri)`
(готовая функция уже есть, `server.py:235`).

**Сознательное ограничение scope: `ObjectModule.bsl` + `RecordSetModule.bsl`,
не более.** Для `ManagerModule.bsl` неявных `Ссылка`/`ЭтотОбъект` нет вообще
(ничего сеять не нужно, гард на имя файла это и так корректно пропускает).

Проверено на реальном коде:

- Модуль набора записей одного из регистров сведений (реальная прикладная
  конфигурация) — `ЭтотОбъект` используется как аргумент вызова
  пользовательской функции, `Ссылка` не встречается вообще (у регистров нет
  ссылочного типа). Тип `ЭтотОбъект` — `РегистрСведенийНаборЗаписей.<Имя>` —
  та же подстановка `"Менеджер"→"НаборЗаписей"`, **независимо
  подтверждённая** уже существующей записью в `RETURN_TYPE_MAP`:
  `"регистрсведенийменеджер.создатьнаборзаписей": "РегистрСведенийНаборЗаписей"`
  — то же самое имя, не придумано заново. Добавлено в scope.
  (Там же встретилась ещё одна неявная переменная набора записей — фильтр
  регистра, — но её тип — специфичная для регистра структура фильтра, не
  метаданные-идентичность; не добавляется.)

- Модуль менеджера значения одной из констант (реальная прикладная
  конфигурация) — проверка показала, что это **другой, не обобщаемый**
  случай, не просто "не уверены — пропускаем": `ЭтотОбъект` там тоже
  используется, но его платформенный тип — `МенеджерЗначенияКонстанты.<Имя>`,
  а не `"КонстантаОбъект"`, которое дала бы подстановка
  `"Менеджер"→"Объект"` — слово не заменяется по общей схеме, у констант
  нет ни `Ссылка`, ни объекта в привычном смысле. Плюс там же встретилась
  переменная `Значение` — тип значения константы из XML (`<Тип>Булево</Тип>`
  и т.п.), требует парсинга XML метаданных константы — отдельный, третий
  механизм. **Остаётся вне scope этой задачи**, возможный отдельный
  follow-up.

## Что не входит в задачу

- Расширение `RETURN_TYPE_MAP` записями, не связанными с целью этой задачи
  (родовые платформенные типы вроде `Структура`/`HTTPОтвет` — см. «Зачем
  это нужно» выше). Пункт 2 выше — целевое исключение, не общий рост «про
  запас».
- Текстовые runtime-проверки типа (`ТипЗнч(X) = Тип("Kind.Name")`) как
  дополнительный источник типовых сигналов — замечено в том же реальном
  коде (сам 1С использует нашу же составную нотацию), но это отдельный,
  не-AST-walk источник, не запрошен для этой задачи.
- Межпроцедурное распространение типа через параметры/возвраты функций —
  отдельная, существенно более сложная задача (вне scope этого документа).
  Эта задача ограничена тем, что видно внутри одной процедуры за один
  проход AST.
- Обращения вне AST (текст запроса `ВЫБРАТЬ Организации.ИНН`, XML форм/
  макетов отчётов) — не решается type-инференсом по определению, другой
  источник данных.
