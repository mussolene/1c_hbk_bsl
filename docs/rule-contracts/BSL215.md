## Описание диагностики

Описание метода (процедуры или функции) должно оформляться корректно, помогая программистам правильно использовать функциональность.

Если метод содержит параметры, то в его описании, в одноименном блоке, должны быть приведены описания для всех параметров в том же порядке, что и в сигнатуре метода.

Диагностика обнаруживает типовые ошибки:

- Отсутствие описания всех параметров
- Отсутствие описания части параметров, с указанием, для какого параметра описание не обнаружено
- Присутствие в описании параметров, отсутстсвующих в сигнатуре метода (которые могли остаться от рефакторинга)
- Некачественное описание параметра: когда имя параметра присутствует в описании метода, но не указаны тип параметра и описание типа

## Description

The description of a method (procedure or function) should be formatted correctly to help programmers use the functionality correctly.

If a method contains parameters, then in its description, in the block of the same name, descriptions for all parameters must be given in the same order as in the method signature.

Diagnostic detects typical errors:

- Lack of description of all parameters
- Absence of a description of some of the parameters, indicating for which parameter the description was not found
- The presence in the description of parameters that are absent in the method signature (which could remain from refactoring)
- Poor parameter description: when the parameter name is present in the method description, but the parameter type and type description are not specified

## Standard And Product Decision

- Standard or product policy: documented methods must keep their parameter documentation synchronized with the method signature.
- Why this diagnostic exists: stale, missing, empty, or out-of-order parameter descriptions make public and internal method contracts misleading.
- Non-goals: do not require every method to have documentation; BSL233 owns public-method documentation presence. Do not validate semantic correctness of type names.
- Keep/drop decision: keep as a BSLLS-compatible documentation consistency diagnostic.

## Semantic Oracle

- Checked language fact: a method has an adjacent documentation comment block and the block's `Параметры` / `Parameters` section does not match the method signature.
- Must diagnose when: a documented method has parameters but no parameter section, a signature parameter has no documented entry, a documented entry is empty or malformed by BSLLS description parsing rules, an entry names a parameter absent from the signature, or documented parameter order differs from signature order when no missing/extra errors exist.
- Must not diagnose when: the method has no adjacent documentation block, the method has no parameters and no parameter descriptions, every parameter has a valid description in signature order, or the doc block is a recognized non-method block such as structure composition.
- Diagnostic anchor token/range: missing all parameters, extra descriptions, and wrong order anchor on the method name; missing/empty individual parameters anchor on the parameter identifier range in the signature.
- Quick-fix target, if any: add, remove, complete, or reorder the parameter documentation entry.

## CST Or Domain Fact Model

- Parser/tree source: `DocumentSnapshot.procedures` plus tree-sitter `line_comment` nodes immediately preceding the method declaration.
- CST/domain object types: `ProcInfo` method signature facts, method-adjacent `line_comment` CST block, parameter section header, parameter description entries, and signature parameter ranges.
- Extracted attributes: method name/range, parameter names/ranges/order, documentation block boundaries, parameter-section entries, valid type-description signal, empty descriptions, extra entries, and documented order.
- Parse-error behavior: only parsed procedures/functions are checked; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: CST selects comment nodes and block boundaries; documentation grammar inside comment text is textual by language convention and may use a bounded BSLLS-compatible mini-parser.

## Examples

### Invalid Examples

1. A documented method with `Параметр` in the signature and no `Параметры:` section.
2. A `Параметры:` section that omits one signature parameter.
3. A parameter entry that has no recognized type/description or appears in a different order than the signature.

### Valid Negative Twins

1. A method with no adjacent documentation block.
2. A documented method whose `Параметры:` entries match all signature parameters in order.
3. A documented method with no parameters and no parameter descriptions.

### Edge Examples

- Comments: only the immediately adjacent `//` block before the method is considered documentation.
- Strings: irrelevant; this rule reads comments and signatures.
- Preprocessor: compiler directives between documentation and method declaration are skipped.
- Multiline: multiline signatures use `ProcInfo` parameter ranges; multiline comment descriptions are handled as continuation lines.
- Nested constructs: not relevant; methods are top-level module members.
- BSL/SDBL variants, if relevant: query text is irrelevant.
