## Standard And Product Decision

- Standard or product policy: query text must not dereference reference-object fields through dot chains because it can force expensive object reads in database queries.
- Why this diagnostic exists: nested query field dereference is a query performance problem and should be replaced with joins or explicit selected fields.
- Non-goals: metadata/type literals such as `ЗНАЧЕНИЕ(...)` / `VALUE(...)`, `ТИП(...)` / `TYPE(...)`, and `ТИПЗНАЧЕНИЯ(...)` / `VALUETYPE(...)`, query metadata source names, comments, and fully commented query text.
- Keep/drop decision: keep as a BSLLS-compatible query performance diagnostic.

## Semantic Oracle

- Checked language fact: a SDBL query expression contains a real column/function argument field chain that dereferences more than one segment through dot.
- Must diagnose when: query text contains chains such as `Alias.Ref.Code`, virtual-table parameter field chains, or `ВЫРАЗИТЬ(...).Nested.Field` that BSLLS SDBL listener treats as nested field access.
- Must not diagnose when: the dotted text is a metadata source name, a metadata literal argument, a comment/string outside extracted query text, or a scalar one-dot alias field that is not in a BSLLS nested-field context.
- Diagnostic anchor token/range: the nested field expression range in the original BSL query string line.
- Quick-fix target, if any: rewrite the query with explicit joins or select the needed field through a separate query source.

## CST Or Domain Fact Model

- Parser/tree source: extracted query text blocks from the current document snapshot; current implementation uses the existing query-line fact stream and SDBL parse availability from the query runtime pool.
- CST/domain object types: query text block content lines, SDBL field/function contexts where available, and original BSL line mapping.
- Extracted attributes: query line number, query head text, field chain text, clause state, metadata-root prefix, metadata-literal call spans, and original LSP range.
- Parse-error behavior: dynamic query fragments are skipped unless the existing query block extractor produced a stable content-line fact.
- Textual/regex behavior, only if genuinely textual: a bounded query-text scanner is retained for BSLLS listener compatibility gaps; valid metadata literal calls are masked before scanning.

## Examples

### Invalid Examples

1. `ВЫБРАТЬ Товары.Ссылка.Код ИЗ Справочник.Номенклатура КАК Товары`.
2. Virtual table parameter list contains `Аналитика.Партнер`.
3. `ВЫРАЗИТЬ(ВТ.Документ КАК Документ.Заказ).Валюта.Код`.

### Valid Negative Twins

1. `ВЫБРАТЬ Товары.Ссылка ИЗ Справочник.Номенклатура КАК Товары`.
2. `ТИП(Документ.ЗаказКлиента)` inside a query condition.
3. `ТИПЗНАЧЕНИЯ(Источник.Документ)` or `ЗНАЧЕНИЕ(Перечисление.Виды.Основной)` inside a query condition.

### Edge Examples

- Comments: fully commented query literals are ignored.
- Strings: non-query BSL strings are not scanned as query diagnostics.
- Preprocessor: no special semantic target beyond extracted query lines.
- Multiline: query text may span several BSL string lines; ranges are mapped per original content line.
- Nested constructs: subqueries and virtual table parameters are checked when extracted as query lines.
- BSL/SDBL variants, if relevant: Russian and English query keywords are supported where the scanner already recognizes them.

## Implementation Decision

- Change target: BSL234 metadata-literal masking in `query_runtime_rules.py`, synthetic negative coverage, contract, and audit state.
- Delta category fixed by this change: semantic mismatch from classifying `ТИП` / `TYPE` metadata literals as dereferenced query fields.
- Why not another layer: the bug is in the existing query-text candidate scanner before chain detection; no new SDBL parser pass is needed.
- Rollback signal: `ТИП(Документ.X)` reports as BSL234, or real `Alias.Ref.Field` stops reporting.
