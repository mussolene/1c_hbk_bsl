## Описание диагностики

При разработке конфигураций, предназначенных для работы в веб-клиенте, запрещено использовать модальные формы и диалоги и синхронные вызовы. В противном случае, конфигурация окажется неработоспособной в ряде веб-браузеров, так как модальные окна не входят в стандарт веб-разработки, а для обеспечения взаимодействия с пользователем требуются асинхронные средства.

## Description

When developing configurations designed to work in the web client, it is forbidden to use modal forms and dialogs and synchronous calls. Otherwise, the configuration will be inoperative in a number of web browsers, since modal windows are not part of the web development standard, and asynchronous tools are required to ensure user interaction.

### Diagnostic restrictions

Currently, **only the use of global context methods** is diagnosed.

## Standard And Product Decision

- Standard or product policy: UI/client code should use asynchronous APIs instead of synchronous calls.
- Why this diagnostic exists: synchronous calls can block the client UI and degrade user experience.
- Non-goals: server-only modules/methods, split module fragments, split layout modules, comments, strings, and unsupported APIs.
- Keep/drop decision: keep as a BSLLS-compatible UI performance diagnostic.

## Semantic Oracle

- Checked language fact: client-capable code calls a known synchronous API from the BSL272 replacement table.
- Must diagnose when: a known sync API call appears in supported non-server-only module code.
- Must not diagnose when: the call is in server-only module/method scope, split fragments/layout modules, comments, strings, or an unsupported call.
- Diagnostic anchor token/range: full synchronous call expression.
- Quick-fix target, if any: use the listed asynchronous replacement.

## CST Or Domain Fact Model

- Parser/tree source: current source lines with string/comment masking plus path/module split gates.
- CST/domain object types: module path, procedure compiler directives, masked call text.
- Extracted attributes: synchronous method name, call range, server-only module/method state, split-fragment/layout state.
- Parse-error behavior: line-local call scan may run; syntax errors remain owned by BSL001.
- Textual/regex behavior, only if genuinely textual: bounded masked call scanner is appropriate because the rule checks a fixed API-name table.

## Examples

### Invalid Examples

1. `УдалитьФайлы("tmp.xml")` in client-capable module code.
2. `ЗапуститьПриложение("app")` in form/client code.
3. `Вопрос("Продолжить?")` in client-capable code.

### Valid Negative Twins

1. Same call inside an `&НаСервере` method.
2. Same call in a split method fragment.
3. Same call inside a string/comment.

### Edge Examples

- Comments: masked before matching.
- Strings: masked before matching.
- Preprocessor: no separate semantic target.
- Multiline: call end helper covers multiline calls.
- Nested constructs: nested statements are checked unless in skipped server/split scope.
