## Описание диагностики

Структура программного модуля _(в общем виде)_ четко определена:

- сначала идет блок определения переменных
- затем определения процедур и функции
- затем блок кода модуля

Исходя из описанной выше структуры, расположение программного кода ранее определения методов недопустимо.

## Примеры

Неправильно

```bsl
Метод();
Сообщить("До описания методов");

Процедура Метод()
// Тело методов
КонецПроцедуры
```

## Description

The structure of the software module *(in general form)* is clearly defined:

- first comes the variable definition block
- then definitions of procedures and functions
- then the module code block

Based on the structure described above, the location of the program code before the definition of methods is unacceptable.

## Examples

Incorrect

```bsl
SomeMethod();
Message("Before methods definition");

Procedure SomeMethod()
// Method body
EndProcedure
```

## Standard And Product Decision

- Standard or product policy: whole program modules should be structured as variable declarations, then procedure/function definitions, then module-body code.
- Why this diagnostic exists: executable module-body code before method definitions violates the standard module layout and makes initialization order harder to reason about.
- Non-goals: split module fragments, extracted single-method files, form fragments, or code inside procedure/function bodies.
- Keep/drop decision: keep as a BSLLS-compatible module-structure diagnostic for whole modules only.

## Semantic Oracle

- Checked language fact: an executable module-body statement appears before the first method definition in a whole module.
- Must diagnose when: a whole module has executable code before the first procedure/function definition.
- Must not diagnose when: only variables, comments, annotations, regions/preprocessor wrappers, or split-fragment markers precede the first method; non-canonical `Ext/*.bsl` fragments are outside this rule.
- Diagnostic anchor token/range: from the first executable body node before the first method through the last relevant pre-method body node, matching BSLLS range policy.
- Quick-fix target, if any: move method definitions before module-body code or move executable code after all method definitions.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter CST root children for whole-module files.
- CST/domain object types: root-level `procedure_definition`, `function_definition`, `preprocessor`, comments, `var_definition`, executable body nodes, and parse-error preprocessor-end markers.
- Extracted attributes: path whole-module status, first method index, pre-method executable span, preprocessor region method containment, source range, and severity.
- Parse-error behavior: orphan `#КонецОбласти` / `#EndRegion` fragments before a method are not executable code; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: only path/module-kind classification and orphan end-region text classification are textual policy around CST facts.

## Examples

### Invalid Examples

1. `Метод(); Процедура Метод() КонецПроцедуры`
2. `Сообщить("До методов"); Функция Значение() Возврат 1; КонецФункции`
3. `А = 1; Процедура П() КонецПроцедуры`

### Valid Negative Twins

1. `Перем Глоб; Процедура П() КонецПроцедуры`
2. `#Область Методы Функция Значение() Возврат 1; КонецФункции #КонецОбласти`
3. Non-canonical `Ext/П.bsl` split fragment containing one method.

### Edge Examples

- Comments: ignored before the first method.
- Strings: only executable statement nodes before the first method report; string contents alone do not.
- Preprocessor: region wrappers and annotations before methods are ignored unless they contain executable body nodes before methods.
- Multiline: diagnostic range follows CST node span and may cover multiple pre-method lines.
- Nested constructs: methods inside preprocessor regions count as first method definitions for this rule.
- BSL/SDBL variants, if relevant: query text is outside this rule.
