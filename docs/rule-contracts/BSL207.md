## Описание диагностики

При написании запросов не следует использовать соединения с виртуальными таблицами. Следует соединять друг с другом только объекты метаданных или временные таблицы.

Если в запросе используется соединение с виртуальной таблицей языка запросов 1С:Предприятия (например, РегистрНакопления.Товары.Остатки) и запрос работает с неудовлетворительной производительностью, то рекомендуется вынести обращение к виртуальной таблице в отдельный запрос с сохранением результатов во временной таблице.

## Description

When writing queries, you should not use virtual tables joins. Only metadata objects or temporary tables should be joined to each other.

If the query uses a join to a virtual table (for example, AccumulationRegister.Products.Balance) and the query is slow, then it is recommended to move the data reading from the virtual table into a separate query with the results saved in a temporary table.

## Standard And Product Decision

- Standard or product policy: query joins should not use virtual tables as joined data sources.
- Why this diagnostic exists: virtual tables in joins can produce inefficient query plans; the preferred pattern is to materialize the virtual table result into a temporary table first.
- Non-goals: do not diagnose a virtual table used as the only data source without any join.
- Keep/drop decision: keep as a BSLLS-compatible query performance diagnostic backed by the 1C standard.

## Semantic Oracle

- Checked language fact: an SDBL virtual table source participates in a join.
- Must diagnose when: a `virtual_table_source` is inside a `join_clause`, or the initial `table_source` is a virtual table and the same table source has one or more join clauses.
- Must not diagnose when: a virtual table source is used without a join.
- Diagnostic anchor token/range: the virtual table call range, including parameters, mapped to BSL query-string coordinates.
- Quick-fix target, if any: move the virtual table call to a separate query and join the resulting temporary table.

## CST Or Domain Fact Model

- Parser/tree source: unescaped SDBL tree-sitter CST from query text blocks.
- CST/domain object types: `QueryTextBlockInfo`, `table_source`, `join_clause`, `virtual_table_source`.
- Extracted attributes: whether the virtual source is inside a join clause, whether the containing table source has join clauses, and mapped BSL line/character range.
- Parse-error behavior: report recovered `virtual_table_source` nodes even when they are nested under an `ERROR` node inside a join clause, matching BSLLS `virtualTable()` recovery on observed private parity deltas.
- Textual/regex behavior, only if genuinely textual: legacy regex fallback may remain only for environments without query block/SDBL facts; valid CST paths must be structural.

## Examples

### Invalid Examples

1. `ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.Товары.Остатки(&Дата) КАК T`.
2. `РегистрНакопления.Товары.Остатки(&Дата) КАК T ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Тест КАК S`.
3. `LEFT JOIN AccumulationRegister.Goods.Balance(&Date) AS T`.

### Valid Negative Twins

1. `ИЗ РегистрНакопления.Товары.Остатки(&Дата) КАК T` with no join.
2. `ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Тест КАК T`.
3. A query text string containing a virtual-table-looking name inside a literal.

### Edge Examples

- Comments: query comments do not produce virtual table CST source nodes.
- Strings: source-like text inside query string literals must not report.
- Preprocessor: BSL preprocessor is irrelevant after query text extraction.
- Multiline: virtual table parameter lists may span several query-string lines.
- Nested constructs: each joined virtual table source is diagnosed at its own call range.
- BSL/SDBL variants, if relevant: Russian and English join syntax are equivalent when parsed by SDBL CST.
