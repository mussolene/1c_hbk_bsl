## Standard And Product Decision

- Standard or product policy: privileged common modules should be named so their full-access/privileged behavior is visible from the module name.
- Why this diagnostic exists: privileged modules bypass ordinary access restrictions; a name without a full-access marker hides an important security/runtime property.
- Non-goals: non-privileged modules, non-common modules, missing/unreadable XML, execution-context naming, and API-region shape.
- Keep/drop decision: keep as a BSLLS-compatible common-module naming diagnostic.

## Semantic Oracle

- Checked language fact: a common module is privileged and its metadata name does not contain a full-access marker.
- Must diagnose when: sibling common-module XML exists, `Privileged` is true, and the module name does not contain `ПолныеПрава` or `FullAccess`.
- Must not diagnose when: XML is missing/unreadable, the module is not privileged, or the name already contains an accepted full-access marker.
- Diagnostic anchor token/range: the first non-empty/non-BOM line of the module file.
- Quick-fix target, if any: rename the common module to include an accepted full-access marker.
