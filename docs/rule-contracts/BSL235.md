## Описание диагностики

При написании текста запроса необходимо следовать следующему правилу: текст запроса должен быть написан таким образом, что бы он мог быть открыт конструктором запросов.

Следование этому правилу позволяет осуществлять быструю проверку корректности синтаксиса запроса, а также доработку и сопровождение.

## Примеры

Неправильно

```bsl
ТекстЗапроса = "ВЫБРАТЬ
| Номенклатура.Наименование  КАК Наименование ,
| Номенклатура. " + ИмяПоляКод + " КАК КодАртикул
|ИЗ
| Справочник.Номенклатура КАК Номенклатура";
```

Правильно

```bsl
ТекстЗапроса = "ВЫБРАТЬ
| Номенклатура.Наименование  КАК Наименование ,
| &ИмяПоляЗапроса КАК КодАртикул
|ИЗ
| Справочник.Номенклатура КАК Номенклатура";

ТекстЗапроса = СтрЗаменить(ТекстЗапроса,
                            "&ИмяПоляКод",
                            "Номенклатура." + ИмяПоляКод);
```

## Description

When writing queries, you must follow the following rule: the query text must be opened by the query designer.

This rule allows you to quickly check the correctness of the syntax of the query, as well as revision and maintenance.

## Examples

Incorrect

```bsl
Text = "SELECT
| Goods.Name  AS Name ,
| Goods. " + FieldNameCode + " AS Code
|From
| Catalog.Goods КАК Goods";
```

Correct

```bsl
Text = "SELECT
| Goods.Name AS Name,
| &FieldNameCode AS Code
|FROM
| Catelog.Goods AS Goods";

Text = StrReplace(Text,
                            "&FieldNameCode",
                            "Goods." + FieldNameCode);
```

## Rule Identity

- Code: BSL235
- BSLLS compatible name: QueryParseError
- Public name/i18n key: QueryParseError / BSL235
- Default message/i18n key: Ошибка разбора текста запроса
- Description/i18n key: Query text parsing error
- Severity: WARNING
- Parameters/defaults: none
- Rule status: parity-classified

## Standard And Product Decision

- Standard or product policy: embedded 1C query text must be syntactically parseable as SDBL when the static literal contains a meaningful query candidate.
- Why this diagnostic exists: malformed query literals fail at runtime and should be reported at development time.
- Non-goals: do not diagnose arbitrary query-looking fragments, dynamic runtime text assembled from unknown values, comments, BSL syntax errors, metadata existence, or semantic query correctness handled by other query rules.
- Keep/drop decision: keep as a BSLLS-compatible query correctness diagnostic with a stricter CST-backed candidate requirement.

## Semantic Oracle

- Checked language fact: a static embedded query text block whose SDBL CST has parse errors and still contains a meaningful partial `query` candidate.
- Must diagnose when: SDBL parsing reports errors and the recovered CST contains a `query` node with `SELECT_KEYWORD` plus real query body evidence such as a non-missing `field` or `from_clause`.
- Must not diagnose when: the parsed text is only a bare `SELECT`/`ВЫБРАТЬ` prefix, a source/field fragment without a recovered `query` node, an empty escaped comparison tail, a valid SDBL tree, or text outside extracted query blocks.
- Diagnostic anchor token/range: the whole recovered SDBL root mapped back to the original BSL query literal range; legacy fallback uses the extracted content line range only when no SDBL root is available.
- Quick-fix target, if any: none.

## CST Or Domain Fact Model

- Parser/tree source: `DocumentSnapshot.query_text_blocks` builds `QueryTextBlockInfo` and parses `query_text` with tree-sitter SDBL.
- CST/domain object types: `QueryTextBlockInfo.sdbl_tree.root_node`, recovered SDBL `query`, `SELECT_KEYWORD`, `field`, and `from_clause` nodes.
- Extracted attributes: `sdbl_has_errors`, root start/end points, recovered query-candidate node presence, and BSL LSP coordinate mapping through `original_lsp_position`.
- Parse-error behavior: parse errors are diagnostic only after the partial SDBL CST contains a meaningful query candidate; raw `ERROR` nodes alone are not diagnostic facts.
- Textual/regex behavior, only if genuinely textual: existing query-block extraction still finds embedded query literals; BSL235 candidate confirmation is CST-based.

## Examples

### Invalid Examples

1. `ВЫБРАТЬ ... ИЗ ... ГДЕ` with a missing condition after `WHERE`/`ГДЕ`.
2. `ВЫБРАТЬ Поле, ИЗ ...` where the recovered tree contains a select body and an SDBL error.
3. `ВЫБРАТЬ (Поле ИЗ ...` with an unclosed parenthesized expression and a recovered query body.

### Valid Negative Twins

1. `ВЫБРАТЬ Поле ИЗ Таблица КАК Т` with no SDBL parse errors.
2. Bare static prefix `ВЫБРАТЬ ` without any recovered query body.
3. Dynamic construction `"ВЫБРАТЬ " + Поля + " ИЗ " + Источник` where the first extracted literal is only a prefix.

### Edge Examples

- Comments: query text line comments are stripped by query-block extraction before SDBL parsing.
- Strings: escaped empty query strings and escaped empty comparison tails are skipped to avoid reporting empty string literal fragments.
- Preprocessor: no special handling; BSL source parsing and line extraction decide visible text.
- Multiline: multiline query literals map recovered SDBL root positions back to original BSL lines.
- Nested constructs: nested SDBL expressions are accepted when the recovered tree has a meaningful query candidate.
- BSL/SDBL variants, if relevant: Russian and English SDBL keywords are accepted by the SDBL parser.

## Implementation Decision

- Change target: `src/onec_hbk_bsl/analysis/diagnostic/rules/query_text_rules.py`.
- Delta category fixed by this change: semantic mismatch where raw or grammar-gap SDBL parse errors were treated as diagnostics without recovered query-candidate and relevant-error evidence, while true partial query bodies were preserved.
- Why not another layer: query extraction still owns finding embedded text; BSL235 specifically owns deciding whether an SDBL parse error is diagnostic.
- Rollback signal: synthetic valid negative twins start reporting BSL235, or parity/performance shows large unexplained regressions.
