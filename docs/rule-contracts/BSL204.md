## Standard And Product Decision

- Standard or product policy: Source files must not contain invisible or lookalike characters that can change readability or behavior.
- Why this diagnostic exists: It flags non-breaking spaces, soft hyphens, and dash variants that should not be present in source code.
- Non-goals: Ordinary ASCII punctuation and allowed Unicode identifiers/strings.
- Keep/drop decision: keep

## Semantic Oracle

- Checked language fact: A source line contains a disallowed character from the BSL204 invalid-character set.
- Must diagnose when: The first disallowed character on a line is found.
- Must not diagnose when: The line contains only allowed characters.
- Diagnostic anchor token/range: the containing string span if inside a string, otherwise the trimmed line span.
- Quick-fix target, if any: replace the invalid character manually.

- Parser/tree source: `DocumentSnapshot.invalid_character_facts`.

- Extracted attributes: line index, invalid character position, anchor range.
- Parse-error behavior: encoding/character scan can run without valid CST.
- Textual/regex behavior, only if genuinely textual: this is a textual encoding hygiene rule.

## Examples

### Invalid Examples

1. A line contains a non-breaking space.
2. A line contains a soft hyphen.
3. A line contains a dash lookalike instead of a normal hyphen.

### Valid Negative Twins

1. A line uses ordinary space.
2. A line uses ordinary hyphen-minus.
3. A line contains allowed Cyrillic or Latin identifier characters.

### Edge Examples

- Comments: invalid characters in comments are still file characters.
- Strings: diagnostic anchors the containing string span when relevant.
- Preprocessor: invalid characters are still file characters.
- Multiline: each physical line is scanned independently.
- Nested constructs: not relevant.
- BSL/SDBL variants, if relevant: embedded query text is still file text.
