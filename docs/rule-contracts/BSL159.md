| Common module type              | Naming example                 | Server call | Server | External connection | Client (Ordinary application) | Client (Managed application) |
| ------------------------------- | ------------------------------ | ----------- | ------ | ------------------- | ----------------------------- | ---------------------------- |
| Server-side                     | Common (or CommonServer)       |             | +      | +                   | +                             |                              |
| Server-side to call from client | CommonServerCall               | +           | +      |                     |                               |                              |
| Client-side                     | CommonClient (or CommonGlobal) |             |        |                     | +                             | +                            |
| Client-server                   | CommonClientServer             |             | +      | +                   | +                             | +                            |

## Standard And Product Decision

- Standard or product policy: a common module must have a valid execution-context flag combination.
- Why this diagnostic exists: invalid common-module context flags make the module unavailable in every supported execution context or represent an impossible module type.
- Non-goals: non-common modules, missing/unreadable XML metadata, XML files without common-module flag data, common-module naming, API regions, and call-site usage.
- Keep/drop decision: keep as a BSLLS-compatible metadata/XML diagnostic.

## Semantic Oracle

- Checked language fact: the common module XML flags do not satisfy any BSLLS valid execution-context predicate.
- Must diagnose when: a `CommonModules/.../Ext/Module.bsl` file has readable sibling common-module XML metadata and its flags are not server, server-call, client, or client-server according to the BSLLS predicate model.
- Must not diagnose when: XML is missing/unreadable, the metadata is not a common module, required flag tags are absent, or any supported execution-context predicate is true.
- Diagnostic anchor token/range: first character of the module file, line 1 character 0-1.
- Quick-fix target, if any: adjust common-module execution flags in metadata.

## CST Or Domain Fact Model

- Parser/tree source: XML metadata next to the common module; BSL text is used only for the diagnostic file/range.
- CST/domain object types: common-module XML properties and boolean execution-context flags.
- Extracted attributes: `Server`, `ServerCall`, `ClientOrdinaryApplication`, `ClientManagedApplication`, and `ExternalConnection`.
- Parse-error behavior: BSL parse errors do not affect this XML-driven rule; malformed/unreadable XML produces no diagnostic.
- Textual/regex behavior, only if genuinely textual: XML tags are currently read by robust textual tag extraction because the needed metadata surface is a small fixed flag set.

## Examples

### Invalid Examples

1. Common module XML where all execution flags are false.
2. Common module with only `Server=true`, without the companion flags required by the BSLLS server predicate.
3. Common module XML whose flag combination satisfies none of server, server-call, client, or client-server.

### Valid Negative Twins

1. Server module: `Server=true`, `ExternalConnection=true`, `ClientOrdinaryApplication=true`, `ClientManagedApplication=false`, `ServerCall=false`.
2. Client module: `ClientOrdinaryApplication=true` and `ClientManagedApplication=true`.
3. Server-call module: `Server=true`, `ServerCall=true`, and no client/external flags.

- Comments: BSL comments are irrelevant.
- Strings: BSL strings are irrelevant.
