## Описание диагностики

В большинстве алгоритмов возможно обойтись без использования оператора `ПОДОБНО`, а в оставшихся необходимо внимательно его использовать, т.к. результат в некоторых ситуациях может сильно отличаться от ожидаемого, например при использовании разных СУБД.

## Примеры

### Правильно

```bsl
Реквизит ПОДОБНО "123%"
```

### Неправильно:

```bsl
Реквизит ПОДОБНО Таблица.Шаблон
```

## Description

In most algorithms, it is possible to do without using the operator `LIKE`, and in the rest, you must use it carefully. The result in some situations can be very different from the expected, for example, when using different DBMS.

## Examples

### Correct

```bsl
Property LIKE "123%"
```

### Incorrect:

```bsl
Property LIKE Table.Template
```

## Standard And Product Decision

- Standard or product policy: query `ПОДОБНО` / `LIKE` usage is discouraged because it can produce unpredictable or slow query plans.
- Why this diagnostic exists: LIKE predicates often prevent efficient indexed search and should be reviewed or replaced.
- Non-goals: do not diagnose BSL string text that is not a successfully parsed SDBL query, comments, malformed partial query fragments without an SDBL `like_expression`, or non-LIKE query predicates.
- Keep/drop decision: keep as a BSLLS-compatible informational query diagnostic.

## Semantic Oracle

- Checked language fact: a parsed SDBL query contains a `like_expression`.
- Must diagnose when: SDBL CST has a `like_expression` produced from `ПОДОБНО` / `LIKE`.
- Must not diagnose when: query text is malformed enough that no SDBL `like_expression` exists, `ПОДОБНО` appears only inside a query string literal/comment, or the BSL string is not a query block.
- Diagnostic anchor token/range: full SDBL `like_expression` range, mapped back to original BSL query-string coordinates.
- Quick-fix target, if any: rewrite the query predicate to use exact/range comparisons, normalized search fields, or another indexed search strategy.

## CST Or Domain Fact Model

- Parser/tree source: unescaped SDBL tree-sitter CST from query text blocks for semantic facts, with the original `QueryTextBlockInfo.sdbl_tree` used only as a coordinate source when it has the same like-expression start.
- CST/domain object types: `QueryTextBlockInfo`, SDBL `like_expression`, unescaped line/byte maps, and original query-head CST ranges.
- Extracted attributes: like-expression start/end row and byte columns, mapped BSL line/character range; original-source range is ignored when it would introduce a `LIKE` fact that does not exist in the unescaped semantic CST.
- Parse-error behavior: no regex fallback when query blocks have SDBL CST available; malformed query fragments are reported only if the SDBL parser still produces a `like_expression`.
- Textual/regex behavior, only if genuinely textual: fallback regex is retained only for environments without SDBL CST/query block facts.

## Examples

### Invalid Examples

1. `ГДЕ Т.Код ПОДОБНО &Шаблон`.
2. `WHERE T.Code LIKE &Pattern`.
3. `ГДЕ Т.Наименование ПОДОБНО "А%"`.

### Valid Negative Twins

1. `ГДЕ Т.Код = &Код`.
2. `ГДЕ Т.Код В (&Коды)`.
3. `ГДЕ Т.Наименование >= &Начало И Т.Наименование < &Конец`.
4. A malformed string fragment containing `ПОДОБНО` but no parsed SDBL `like_expression`.

### Edge Examples

- Comments: SDBL comments do not produce `like_expression`.
- Strings: `ПОДОБНО` / `LIKE` inside SDBL string literals must not report.
- Preprocessor: BSL preprocessor is irrelevant after query text extraction.
- Multiline: like expressions may span query-string lines; mapped range may span BSL lines.
- Nested constructs: LIKE inside nested query expressions is diagnosed the same way.
- BSL/SDBL variants, if relevant: SDBL CST is the source of truth.
