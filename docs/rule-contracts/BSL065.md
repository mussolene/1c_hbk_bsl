## Описание диагностики

Описание метода (процедуры или функции) должно оформляться корректно, помогая программистам правильно использовать функциональность.

Описание функции должно содержать описание возвращаемого значения в одноименном блоке. Необходимо привести описание для всех возможных типов возвращаемого значения.

Диагностика обнаруживает типовые ошибки:

- Отсутствие описания возвращаемого значения
- Наличие описания возвращаемого значения у процедуры
- Некачественное описание возвращаемого значения: когда имя типа присутствует в описании, но не указано его описание
  - Для активации этой, более строгой проверки, необходимо снять разрешение краткой формы записи параметром диагностики

## Description

The description of a method (procedure or function) should be formatted correctly to help programmers use the functionality correctly.

The function description must contain a description of the return value in the block of the same name. You must provide a description for all possible return types.

Diagnostics detects typical errors:

- No return value description
- Return value description for procedure
- Poor description of the return value: when the type name is present in the description, but its description is not specified
  - To activate this more stringent check, you must turn off the short form permission by the diagnostic parameter

## Standard And Product Decision

- Standard or product policy: function documentation should describe returned values in a `Возвращаемое значение` / `Returns` section.
- Why this diagnostic exists: undocumented function returns make API contracts ambiguous and harder to safely reuse.
- Non-goals: full EDT documentation rendering, exact replication of every legacy BSLLS comment parser quirk, or checking procedure return values as language semantics.
- Keep/drop decision: keep as a BSLLS-compatible method-documentation diagnostic, with explicitly classified parser-context deltas.

## Semantic Oracle

- Checked language fact: a function doc-comment block lacks a valid returned-value section entry, or a procedure doc-comment incorrectly contains a returned-value section.
- Must diagnose when: a documented function has no returned-value section, the section has no parseable entry, or a procedure has a returned-value section.
- Must not diagnose when: a function has a valid returned-value section entry, a short returned-value description is parseable under the default policy, or a comment redirects with `См.` / `See`.
- Diagnostic anchor token/range: method name in the declaration line.
- Quick-fix target, if any: add a returned-value section entry for functions or remove the returned-value section from procedures.

## CST Or Domain Fact Model

- Parser/tree source: procedure facts plus contiguous `//` doc-comment block immediately preceding the method, skipping compiler directives.
- CST/domain object types: `ProcedureModel`, comment block, returned-value section line, returned-value entry line, and method name span.
- Extracted attributes: method kind/export flag, method name range, preceding comment block, returns-section position, inline return text, entry text, redirect marker, legacy module path state, and severity.
- Parse-error behavior: relies on extracted procedure facts; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: documentation comments are textual by nature; parsing is limited to BSL/BSLLS documentation headings and entries.

## Examples

### Invalid Examples

1. `// Описание функции` before `Функция Тест()`.
2. `// Возвращаемое значение:` followed only by `//   -`.
3. `// Возвращаемое значение:` before `Процедура Тест()`.

### Valid Negative Twins

1. `// Возвращаемое значение:\n//   Число - результат` before a function.
2. `// Возвращаемое значение - Булево - результат` before a function.
3. `// См. ДругойМетод` before a function.

### Edge Examples

- Comments: only contiguous doc-comment lines directly before a method are considered.
- Strings: ignored because only comments are inspected.
- Preprocessor: compiler directives between comment and method are skipped.
- Multiline: returned-value entries may be on lines after the section heading; inline heading text is also supported.
- Nested constructs: not relevant; method declarations define the documentation target.
