## Standard And Product Decision

- Standard or product policy: platform 8.3.17 introduced `ОбработкаОшибок`; old global error presentation methods are deprecated.
- Why this diagnostic exists: code targeting compatibility 8.3.17+ should call same-named methods on `ОбработкаОшибок` instead of deprecated global context methods.
- Non-goals: object/member calls, comments, strings, compatibility modes below 8.3.17, and unrelated error APIs.
- Keep/drop decision: keep as a BSLLS-compatible deprecated API diagnostic.

## Semantic Oracle

- Checked language fact: executable BSL code calls a deprecated 8.3.17 global method.
- Must diagnose when: `КраткоеПредставлениеОшибки`, `ПодробноеПредставлениеОшибки`, or `ПоказатьИнформациюОбОшибке` is called globally in a configuration with compatibility 8.3.17 or higher, or with no known lower compatibility.
- Must not diagnose when: the method is a member/object call, text inside string/comment, or project compatibility is below 8.3.17.
- Diagnostic anchor token/range: deprecated method name.
- Quick-fix target, if any: qualify the call through `ОбработкаОшибок` or apply the project error-handling wrapper.

## CST Or Domain Fact Model

- Parser/tree source: masked source lines and configuration compatibility metadata.
- CST/domain object types: textual global-call facts with `(?<!\\.)` member-call guard.
- Extracted attributes: compatibility version tuple, clean code line, matched method name, and method-name range.
- Parse-error behavior: syntax-error structure is not required; masked textual calls still report when the global-call spelling is clear.
- Textual/regex behavior, only if genuinely textual: regex is acceptable because this rule checks a small exact global-method spelling set and masks comments/strings before matching.
