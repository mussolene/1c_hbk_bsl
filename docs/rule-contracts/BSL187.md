## Описание диагностики

Диагностика проверяет поля из левых, правых, полных соединений, для которых не выполняется проверка с помощью `ЕСТЬNULL()` или `НЕ ЕСТЬ NULL` или или `ЕСТЬ НЕ NULL`.

В запросах нельзя использовать реквизиты из присоединяемых слева или справа таблиц без проверки значений на `NULL`.
Указанное обращение может приводить к ошибкам, если условие соединения не выполнено и нет подходящих записей в левой или правой таблице.
В итоге в результате запроса можно получить неожиданные данные и система может повести себя неверным образом.

Важно помнить, что любое сравнение значения `NULL` с любым другими выражением всегда ложно, даже сравнение `NULL` и `NULL` всегда ложно.
Смотрите ниже пример подобных неверных сравнений.
Поэтому нужно правильно выполнять сравнение с `NULL` - или через оператор `ЕСТЬ NULL` или через функцию `ЕСТЬNULL()`.

Также достаточно часто используются левые\правые соединения, хотя данные позволяют использовать внутреннее соединение, в этом случае не нужны проверки на `NULL`.

Или дополнительные проверки реквизитов выполняются в коде 1С, а не в тексте запроса. Подобные обращения затрудняют чтение кода и рефакторинг кода, т.к. контекст обращения к реквизиту приходится учитывать в нескольких местах.
В дополнение нужно учитывать, что простые проверки в запросе выполняются чуть быстрее и проще, чем в интерпретируемом коде 1С.

Указанные проблемы являются одними из самых частых ошибок разработчиков 1С самого разного уровня компетенций.

## Description

Diagnostics checks fields from left, right, full joins that are not checked with `ISNULL()` or `IS NOT NULL`  or `NOT IS NULL` .

Queries cannot use attributes from left-join or right-join tables without checking the values for `NULL`.
Such a call can lead to errors if the join condition is not met and there are no matching records in the left or right table.
As a result, as a result of executing the query, you may receive unexpected data and the system may behave in an incorrect way.

It is important to remember that any comparison of the value `NULL` with any other expression is always false, even the comparison of `NULL` and `NULL` is always false.
The following are examples of such incorrect comparisons.
It is correct to compare with `NULL` - operator `IS NULL` or function `ISNULL()`.

Left \ right joins are often used, although the data allows an inner join without checking for `NULL`.

Additional checks of field values can be performed in the 1C code, and not in the query text. This makes it difficult to read the code and refactor the code, because the context of the access to the field has to be considered in several places.
It should be remembered that simple checks in a query are performed a little faster and easier than in interpreted 1C code.

These problems are the most common mistakes made by 1C developers of all skill levels.

## Examples

Example showing NULL comparison problems - joining 2 tables incorrectly and showing different comparison methods
```sdbl
SELECT
  CASE
    WHEN LeftTable.Fld2 = 0 THEN "Equals 0 - does not work"
    WHEN LeftTable.Fld2 <> 0 THEN "NOT Equals 0 - does not work"
    WHEN LeftTable.Fld2 = NULL THEN "Equals NULL - does not work"
    WHEN LeftTable.Fld2 IS NULL THEN "IS NULL - it works"
    WHEN ISNULL(LeftTable.Fld2, 0) = 0  THEN "ISNULL() - and this works too"
    ELSE "else"
  END
ИЗ
  First AS First
  LEFT JOIN LeftTable AS LeftTable
  ON FALSE
```

## Standard And Product Decision

- Standard or product policy: fields from nullable sides of outer joins must be protected by `ЕСТЬNULL()`/`ISNULL()` or by an explicit `ЕСТЬ НЕ NULL` / `IS NOT NULL` filter when the query intentionally eliminates NULL rows.
- Why this diagnostic exists: values from left, right, and full joins may be `NULL`; using them directly in selected fields, predicates, or other join conditions can produce unexpected results.
- Non-goals: proving metadata nullability, rewriting joins, reporting inner joins, or diagnosing syntactically broken SDBL fragments.
- Keep/drop decision: keep, with BSLLS-compatible outer-join semantics.

## Semantic Oracle

- Checked language fact: an alias from the nullable side of an outer join is used without local NULL protection.
- Must diagnose when: a left-join joined alias, right-join base alias, or either side of a full join is referenced in selected fields, WHERE conditions, or another join condition without `ЕСТЬNULL()`/`ISNULL()` or an effective not-null predicate.
- Must not diagnose when: the field is inside `ЕСТЬNULL()`/`ISNULL()`, the nullable alias is globally filtered by `ЕСТЬ НЕ NULL` / `IS NOT NULL` in WHERE, the join is inner-only, or no reliable outer-join facts can be extracted from the SDBL CST.
- Diagnostic anchor token/range: BSLLS anchors the primary diagnostic on the `joinPart` / SDBL `join_clause`; related information points at unsafe field uses.
- Quick-fix target, if any: wrap the field with `ЕСТЬNULL()` or replace the outer join with an inner join when the not-null filter is intentional.

## CST Or Domain Fact Model

- Parser/tree source: `SemanticFactSnapshot.queries`, populated once from
  `DocumentSnapshot.query_text_blocks` and tree-sitter SDBL CST.
- CST/domain object types: `select_section`, `join_clause`, nullable join aliases, `field_list`, `where_clause`, `dotted_identifier`, `null_check_expression`.
- Extracted attributes: join kind, nullable alias, unsafe dotted identifier, join clause range, containing select-section identity.
- Parse-error behavior: do not fail the whole query block solely because `sdbl_has_errors` is true; report only if tree-sitter still exposes complete nullable `join_clause` facts. Broken fragments with no reliable join facts stay silent.
- Textual/regex behavior, only if genuinely textual: none for valid SDBL paths.

## Examples

### Invalid Examples

1. `ЛЕВОЕ СОЕДИНЕНИЕ ... КАК Левое` and selected field `Левое.Поле`.
2. `ПРАВОЕ СОЕДИНЕНИЕ ...` and selected field from the base alias.
3. `ПОЛНОЕ СОЕДИНЕНИЕ ...` and selected fields from either side.

### Valid Negative Twins

1. `ЕСТЬNULL(Левое.Поле, 0)` in selected fields.
2. `ГДЕ Левое.Ссылка ЕСТЬ НЕ NULL` before using `Левое` fields.
3. `ВНУТРЕННЕЕ СОЕДИНЕНИЕ` with direct field access.

### Edge Examples

- Comments: comments inside query text do not affect alias facts.
- Strings: only recognized query text blocks are parsed as SDBL.
- Preprocessor: BSL preprocessor does not affect SDBL facts after query extraction.
- Multiline: embedded query string lines map through `QueryTextBlockInfo.original_lsp_position`.
- Nested constructs: nested select sections are separate nullable-alias scopes.
- BSL/SDBL variants, if relevant: SDBL CST is required; invalid SDBL is skipped.
