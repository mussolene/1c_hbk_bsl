## Standard And Product Decision

- Standard or product policy: program modules should not expose global module variables with `Экспорт`; use safer platform mechanisms or explicit APIs.
- Why this diagnostic exists: exported module variables create uncontrolled shared state and hard-to-reproduce defects.
- Non-goals: non-export module variables, local `Перем` declarations inside methods, missing variable descriptions, or global-state usage analysis.
- Keep/drop decision: keep as a BSLLS-compatible standard/design diagnostic.

## Semantic Oracle

- Checked language fact: a module-level variable declaration contains `Экспорт` / `Export`.
- Must diagnose when: `Перем ... Экспорт;` / `Var ... Export;` appears outside any procedure/function body, once per declared variable.
- Must not diagnose when: the variable declaration is local to a method or has no export keyword.
- Diagnostic anchor token/range: each variable name start through the end of the export keyword, matching BSLLS range policy.
- Quick-fix target, if any: remove `Экспорт`, replace with method API, or move state to an approved platform object/property.

## CST Or Domain Fact Model

- Parser/tree source: procedure facts define method spans; module-level declarations are checked on clean comment-masked lines outside those spans.
- CST/domain object types: `ProcInfo` start/end lines, module-level line, export variable declaration, individual variable names, and export keyword range.
- Extracted attributes: method body line set, declaration line, names segment, variable start column, export end column, and severity.
- Parse-error behavior: uses extracted procedure spans where available; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: module-level `Перем` declaration matching is textual after comment masking because the target syntax is a simple declaration line.
