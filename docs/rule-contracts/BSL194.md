## Standard And Product Decision

- Standard or product policy: a function should not have multiple return paths that always return the same primitive value.
- Why this diagnostic exists: repeated identical primitive returns usually mean dead branching or an unfinished branch-specific result.
- Non-goals: do not diagnose functions with one return; do not diagnose non-primitive expressions; do not diagnose attachable functions when the default skip policy applies.
- Keep/drop decision: keep as a BSLLS-compatible redundant-return diagnostic.

## Semantic Oracle

- Checked language fact: a non-attachable function has more than one return statement and all returned primitive expressions are the same value under case-insensitive string comparison by default.
- Must diagnose when: more than one `Возврат` / `Return` returns the same primitive literal value and no non-primitive return expression is found.
- Must not diagnose when: there is only one return, return expressions differ, any return expression is non-primitive, or the function name starts with `Подключаемый_` / `Attachable_`.
- Diagnostic anchor token/range: function identifier token.
- Quick-fix target, if any: simplify control flow or return meaningful branch-specific values.

## Examples

### Invalid Examples

1. Function with two branches both returning `Истина`.
2. Function with two returns both returning the same number.
3. Function with two returns both returning the same string ignoring case by default.

### Valid Negative Twins

1. Function with only one return.
2. Function with returns `Истина` and `Ложь`.
3. Function named `Подключаемый_...` with same primitive returns.

### Edge Examples

- Comments: stripped before simple return matching.
- Strings: string literals are primitive and compared case-insensitively by default.
- Preprocessor: parsed body lines are scanned under the same simple return model.
- Multiline: multiline return expressions are not part of the current supported surface.
- Nested constructs: returns inside the same function body count; nested routine behavior should remain owned by parser/procedure facts.
- BSL/SDBL variants, if relevant: query text is irrelevant.
