## Описание диагностики

В исходном тексте многострочные константы могут задаваться двумя способами:

- 'классический', в котором используется символ переноса строки и конкатенация строк
- 'странный', при котором строки разделяются пробельными символами

Второй способ усложняет восприятие, при его использовании проще допустить и пропустить ошибку.

## Примеры

Усложняет восприятие:

```bsl
Строка = "ВВВ" "СС"
"Ф";
```

Классический вариант:

```bsl
Строка = "ВВВ" + "СС"
         + "Ф";
```

## Description

In source text, multi-line constants can be initialized in two ways:

- 'classic', which uses line feed and string concatenation
- 'crazy' where lines are separated by whitespace

The second method complicates the perception; when using it, it is easy to make and miss a mistake.

## Examples

Difficulty understanding:

```bsl
String = "BBB" "CC"
"F";
```

Classic variant:

```bsl
String = "BBB" + "CC"
         + "F";
```

## Standard And Product Decision

- Standard or product policy: adjacent string literals should not rely on implicit multiline/string continuation; explicit `+` concatenation is the readable form.
- Why this diagnostic exists: `"..."\n"..."` and `"... "..."` are easy to misread and usually indicate an accidental missing `+`.
- Non-goals: ordinary escaped quotes inside one string, comments, query pipe text, and valid concatenation with `+`.
- Keep/drop decision: keep as a BSLLS-compatible convention diagnostic.

## Semantic Oracle

- Checked language fact: source contains two adjacent BSL string literal spans separated only by whitespace on one line or across two physical lines.
- Must diagnose when: a complete string literal is immediately followed by another string literal without an operator.
- Must not diagnose when: the literals are connected with `+`, appear in comments, are escaped quotes inside one literal, or the next literal belongs to a comment-only predecessor.
- Diagnostic anchor token/range: from the opening quote of the first literal to the closing quote of the second literal.
- Quick-fix target, if any: insert `+` between the literals or merge them deliberately.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter BSL error nodes plus a small BSL string-span scanner over physical lines.
- CST/domain object types: `ERROR` nodes for parser-recovered adjacent literals; textual string literal spans before comments for stable range construction.
- Extracted attributes: first literal start, second literal end, physical line indexes, comment boundary, and whitespace-only separator.
- Parse-error behavior: parser `ERROR` nodes are accepted only when the scanner can confirm adjacent string literal spans.
- Textual/regex behavior, only if genuinely textual: scanner is used because the rule is about malformed textual adjacency and parser output may be partial.

## Examples

### Invalid Examples

1. `Строка = "А" "Б";`
2. `Строка = "А"` followed by `"Б";` on the next physical line.
3. `Параметр = "Начало"` followed by `"Окончание"` without `+`.

### Valid Negative Twins

1. `Строка = "А" + "Б";`
2. `Строка = "А ""Б""";`
3. `// "А"` followed by `"Б";`.

### Edge Examples

- Comments: strings inside comments are ignored and cannot start the cross-line pair.
- Strings: doubled quotes are treated as escapes inside a single BSL literal.
- Preprocessor: not a separate semantic target.
- Multiline: two-line adjacent literals are reported as one cross-line range.
- Nested constructs: nesting inside calls or assignments does not change adjacency semantics.
- BSL/SDBL variants, if relevant: SDBL query pipe text is outside this rule.
