# BSL030 SemicolonPresence Contract

## Rule Identity

- Code: BSL030
- BSLLS compatible name: SemicolonPresence
- Public name/i18n key: BSL030 / SemicolonPresence
- Default message/i18n key: RULE_MESSAGES_RU["BSL030"]
- Description/i18n key: RULE_METADATA["BSL030"].description
- Severity: INFORMATION
- Parameters/defaults: none; BSLLS configuration can disable `SemicolonPresence`.
- Rule status: verified

## Standard And Product Decision

- Standard or product policy: executable BSL statements inside procedures/functions should explicitly terminate with `;`; procedure/function boundary keywords are not statements and must not require `;`.
- Why this diagnostic exists: explicit terminators remove ambiguity, keep style consistent, and match BSLLS standard/badpractice policy.
- Non-goals: method headers, method endings, standalone semicolon empty statements, syntax-error ownership, formatter insertion, and statements where CST already contains `;`.
- Keep/drop decision: keep as a BSLLS-compatible style/standard diagnostic.

## Semantic Oracle

- Checked language fact: a parsed executable BSL statement that requires a semicolon has no semicolon terminator.
- Must diagnose when: a supported statement node is cleanly parsed and has no `;` token/terminator at the statement end.
- Must not diagnose when: the node is a procedure/function header or footer, the statement has `;`, the only issue is an empty standalone `;` owned by BSL025, the CST subtree has parse errors owned by BSL001, or the code is in comments/strings/query text.
- Diagnostic anchor token/range: BSLLS-compatible statement-ending anchor: normally the last meaningful token; if the statement ends with `)`, the closing parenthesis token.
- Quick-fix target, if any: insert `;` after the statement.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter BSL CST.
- CST/domain object types: `assignment_statement`, `break_statement`, `call_statement`, `continue_statement`, `for_each_statement`, `for_statement`, `if_statement`, `return_statement`, `rise_error_statement`, `try_statement`, `var_statement`, and `while_statement`.
- Extracted attributes: statement node type, child `;` presence, clean/error subtree state, last meaningful leaf token, start/end points, and special `while_statement` terminator byte check.
- Parse-error behavior: statements with parse-error subtrees are skipped; BSL001 owns malformed syntax.
- Textual/regex behavior, only if genuinely textual: none for valid CST paths.

## Examples

### Invalid Examples

1. `Значение = 1`
2. `Сообщить("missing")`
3. `Возврат Значение`

### Valid Negative Twins

1. `Значение = 1;`
2. `Сообщить("ok");`
3. `Процедура Тест()` and `КонецПроцедуры` without semicolons.

### Edge Examples

- Comments: commented code is ignored.
- Strings: multiline string contents are not standalone statements; the containing statement is checked.
- Preprocessor: not a separate semantic target for this rule.
- Multiline: diagnostic anchors the last meaningful token of the parsed multiline statement.
- Nested constructs: control statements and their endings require the terminator policy when represented by supported statement nodes.
- BSL/SDBL variants, if relevant: SDBL query text is not a BSL030 target.

## Implementation Decision

- Change target: BSL030 closing-parenthesis anchor policy, contract, and audit state.
- Delta category fixed by this change: high-volume range-only deltas for call-like statements ending with `)`.
- Why not another layer: CST directly exposes executable statement nodes and semicolon children.
- Rollback signal: method headers require semicolons, standalone semicolons report as BSL030, clean unterminated statements stop reporting, or parse-error fragments produce BSL030 instead of BSL001.
