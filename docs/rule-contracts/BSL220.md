# BSL220 Contract

- Severity: INFORMATION
- Parameters/defaults: no user parameters
- Rule status: verified

## Standard And Product Decision

- Standard or product policy: query text should not contain SDBL multi-line string literals because they are suspicious and can be parsed unpredictably.
- Why this diagnostic exists: multi-line string literals inside query text are easy to confuse with ordinary BSL multiline query strings and can break query readability.
- Non-goals: diagnosing ordinary BSL multiline query text, escaped empty SDBL strings, or non-query BSL string literals.
- Keep/drop decision: keep as a BSLLS-compatible SDBL query-text diagnostic.

## Semantic Oracle

- Checked language fact: after BSL string escaping is resolved, the parsed SDBL query contains a string literal whose CST range crosses query lines.
- Must diagnose when: the embedded query contains a real multi-line SDBL string literal (`string.start_point.row != string.end_point.row` after BSL quote unescaping).
- Must not diagnose when: the query contains a normal escaped empty string such as a single `""""""""` run in BSL source, a single SDBL string token, comments, or non-query text.
- Diagnostic anchor token/range: the SDBL multi-string span mapped back to the original BSL query string lines.
- Quick-fix target, if any: rewrite the query expression to avoid multi-line string literals.

## CST Or Domain Fact Model

- Parser/tree source: embedded query blocks from `DocumentSnapshot` and their tree-sitter SDBL parse tree.
- CST/domain object types: `QueryTextBlockInfo`, temporary unescaped SDBL parse tree, SDBL `string` nodes, original query content-line mapping.
- Extracted attributes: SDBL string node start/end points and UTF-8 byte-offset mapping from unescaped SDBL text back to original BSL line/column.
- Parse-error behavior: if no SDBL tree exists, BSL220 emits no diagnostic.
- Textual/regex behavior, only if genuinely textual: no raw BSL quote-run regex is used for valid SDBL paths.

## Examples

### Invalid Examples

1. Query text where an unescaped SDBL string literal starts on one query line and closes on the next.
2. Query text where a mistaken single quote marker causes a string literal to consume the next query line.
3. Query text where a multi-line SDBL string appears inside a query expression.

### Valid Negative Twins

1. Query text with one normal escaped empty string represented in BSL source as `""""""""`.
2. Query text without any SDBL string token.
3. A non-query BSL multiline string containing quote runs.

### Edge Examples

- Comments: comments are not string tokens.
- Strings: ordinary BSL strings outside query blocks are ignored.
- Preprocessor: preprocessor directives do not matter.
- Multiline: ordinary BSL multiline query text is only the carrier; the target is the SDBL string fact inside it.
- Nested constructs: string tokens inside SDBL function calls are considered when they form a multi-string fact.
- BSL/SDBL variants, if relevant: SDBL is the target grammar.

## Implementation Decision

- Change target: BSL220 query text implementation in `query_text_rules.py`.
- Delta category fixed by this change: ours-only false positives from raw escaped quote runs.
- Why not another layer: the rule needs BSL-unescaped SDBL facts, but changing shared query extraction would risk unrelated query diagnostics in the same batch.
- Rollback signal: escaped empty query strings report again, the upstream-shaped real cross-line string fixture loses its diagnostic, or private parity regains BSL220 deltas.
