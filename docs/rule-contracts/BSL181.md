## Rule Identity

- Code: BSL181
- BSLLS compatible name: DuplicatedInsertionIntoCollection
- Public name/i18n key: BSL181 / DuplicatedInsertionIntoCollection
- Default message/i18n key: RULE_MESSAGES_RU["BSL181"]

- Severity: WARNING
- Parameters/defaults: BSLLS has `isAllowedMethodADD=true`; onec supports `Добавить/Add` and `Вставить/Insert` literal-like facts.
- Rule status: verified

## Standard And Product Decision

- Standard or product policy: inserting or adding the same key/value to the same collection in one straight-line construction block is suspicious and often overwrites or duplicates configuration data.
- Why this diagnostic exists: duplicate collection population statements are usually copy-paste errors.
- Non-goals: full dataflow proving for arbitrary variables, branch-sensitive equivalence, values rebuilt through mutable temporary objects, and exact semantic equality of arbitrary expressions.
- Keep/drop decision: keep as a BSLLS-compatible correctness diagnostic with a local noise guard for mutable/builder patterns.

## Semantic Oracle

- Checked language fact: the same collection target receives repeated literal-like insertion facts in one method body.
- Must diagnose when: a second straight-line `Target.Вставить/Insert(firstArg, ...)` or `Target.Добавить/Add(firstArg, ...)` repeats a normalized supported first argument for the same target.
- Must not diagnose when: the target is reassigned before the repeated insertion, the argument variable is reassigned before repeated `Add`, the duplicate is inside skipped control-flow depth, or the argument is an unsupported arbitrary expression.
- Diagnostic anchor token/range: the duplicate insertion/addition call from target name through the outer call closing parenthesis.
- Quick-fix target, if any: remove the duplicate insertion or change the duplicated key/value.

## CST Or Domain Fact Model

- Parser/tree source: procedure-domain line scan over comment-stripped lines.
- CST/domain object types: procedure body lines, collection insertion facts, target assignment reset facts.
- Extracted attributes: target name, method name, first argument text, normalized argument key, call range, target reassignment, argument-variable reassignment, and shallow control-flow depth.
- Parse-error behavior: broken code should not be aggressively diagnosed; BSL001 owns malformed syntax.
- Textual/regex behavior, only if genuinely textual: line scanning is used because the fact is a small exact method-call surface and must tolerate split-module fragments.

## Examples

### Invalid Examples

1. `Коллекция.Вставить("Ключ");` repeated later in the same straight-line block.
2. `Массив.Добавить("Значение");` repeated later in the same straight-line block.
3. `Карта.Вставить(Префикс + ".Поле", Значение);` repeated with the same normalized first argument.

### Valid Negative Twins

1. `Коллекция = Новый Структура;` between two same-key insertions resets collection facts.
2. `Условие = Новый Структура; Результат.Добавить(Условие);` repeated after reassigning `Условие` does not report.
3. Duplicate-looking calls inside a skipped branch/control depth are not reported by onec to avoid branch noise.

### Edge Examples

- Comments: ignored by the comment-stripped line source.
- Strings: quoted first arguments are preserved and normalized.
- Preprocessor: not a separate semantic target.
- Multiline: current extractor is line-local.
- Nested constructs: nested calls in the first argument are supported for `КодСимвола/CharCode` and string-containing expressions.
- BSL/SDBL variants, if relevant: query text is outside this rule.
