## Описание диагностики

Необязательные параметры (параметры со значениями по умолчанию) должны располагаться после обязательных параметров (без значений по умолчанию).

## Примеры

```bsl
Функция КурсВалютыНаДату(Валюта, Дата = Неопределено) Экспорт
```

## Источники

* [Стандарт: Параметры процедур и функций](https://its.1c.ru/db/v8std#content:640:hdoc)

## Description

Optional parameters (parameters with default values) should follow mandatory parameters (the ones without default values).

## Examples

```bsl
Function CurrencyRateOnDate(Currency, Date = Notdefined) Export
```

## Sources

* [Standard: Parameters of procedures and functions (RU)](https://its.1c.ru/db/v8std#content:640:hdoc)

## Standard And Product Decision

- Standard or product policy: procedure and function signatures should list required parameters before parameters that have default values.
- Why this diagnostic exists: a required parameter after an optional one makes method calls harder to read and easier to misuse.
- Non-goals: reporting parameter count, by-value/reference passing, unused parameters, missing parameter descriptions, or call-site arity.
- Keep/drop decision: keep as a BSLLS-compatible method-contract diagnostic.

## Semantic Oracle

- Checked language fact: a procedure or function parameter list contains a required parameter after at least one parameter with a default value.
- Must diagnose when: any parameter without a default value appears after a previous parameter with a default value in the same method declaration.
- Must not diagnose when: all required parameters precede defaulted parameters, all parameters have defaults, no parameters have defaults, the method has no parameters, or the syntax tree is invalid.
- Diagnostic anchor token/range: the full parameter-list content range, excluding parentheses when CST parameter ranges are available.
- Quick-fix target, if any: reorder the declaration and call sites manually; no automatic quick-fix is provided.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter BSL CST converted into `ProcInfo` by the document snapshot.
- CST/domain object types: `procedure_definition`, `function_definition`, `parameters`, `parameter`, `ProcInfo.params`, `ProcInfo.optional_params`, and parameter-list range fields.
- Extracted attributes: parameter names in declaration order, whether each parameter has a default value, method kind/name, and parameter-list start/end coordinates.
- Parse-error behavior: structural method-contract checks skip invalid trees; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: none for valid CST paths.

## Examples

### Invalid Examples

1. `Процедура Тест(Парам1 = Неопределено, Парам2)`.
2. `Функция Тест(Знач Парам1 = 0, Знач Парам2)`.
3. Multiline signature where `Парам2` follows `Парам1 = Неопределено`.

### Valid Negative Twins

1. `Процедура Тест(Парам1, Парам2 = Неопределено)`.
2. `Процедура Тест(Парам1 = Неопределено, Парам2 = 1)`.
3. `Процедура Тест(Парам1, Парам2)`.

### Edge Examples

- Comments: comments near the signature do not change parameter order facts.
- Strings: default values containing text or commas are still default values.
- Preprocessor: not a separate semantic target.
- Multiline: parameter-list range spans from first parameter to last parameter.
- Nested constructs: expressions inside default values do not create separate BSL228 facts.
- BSL/SDBL variants, if relevant: SDBL is not relevant.
