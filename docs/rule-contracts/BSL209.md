## Standard And Product Decision

- Standard or product policy: query join conditions should not use logical `OR` over different fields.
- Why this diagnostic exists: `OR` in join conditions can prevent index usage and lead to expensive scans and blocking.
- Non-goals: do not diagnose `OR` outside join conditions, and do not diagnose `OR` alternatives over the same field.
- Keep/drop decision: keep as a BSLLS-compatible query performance diagnostic backed by the 1C standard.

## Semantic Oracle

- Checked language fact: an `OR` operator appears in a join condition expression whose local logical branch references more than one distinct field.
- Must diagnose when: `OR_KEYWORD` is inside a `join_clause` condition and the nearest enclosing `binary_expression` contains more than one distinct `dotted_identifier`.
- Must not diagnose when: `OR` is outside a join condition, or all field references in the OR branch are the same field.
- Diagnostic anchor token/range: the `OR_KEYWORD` token range, mapped to BSL query-string coordinates.
- Quick-fix target, if any: split predicates into separate query packages and combine with `UNION ALL`, or materialize an intermediate temporary table.

## CST Or Domain Fact Model

- Parser/tree source: unescaped SDBL tree-sitter CST from query text blocks.
- CST/domain object types: `QueryTextBlockInfo`, `join_clause`, `binary_expression`, `OR_KEYWORD`, `dotted_identifier`.
- Extracted attributes: nearest binary-expression ancestor for each OR token, distinct field identities inside that expression, and mapped BSL line/character range; field identity is the last dotted field segment, and reference types after `ССЫЛКА` are not counted as fields.
- Parse-error behavior: skip malformed query fragments that do not produce the relevant join-condition OR subtree.
- Textual/regex behavior, only if genuinely textual: legacy regex fallback may remain only for environments without query block/SDBL facts; valid CST paths must be structural.

## Examples

### Invalid Examples

1. `ПО A.Код = B.Код И (A.Сумма > 0 ИЛИ A.СуммаНДС > 0)`.
2. `ПО A.Код = B.Код ИЛИ A.Номер = B.Номер`.
3. A nested join condition with `ИЛИ` between different field predicates.

### Valid Negative Twins

1. `ПО A.Код = B.Код И (A.Сумма > 0 ИЛИ A.Сумма < 10)`.
2. `ГДЕ A.Сумма > 0 ИЛИ A.СуммаНДС > 0`.
3. A query text string literal containing the word `ИЛИ`.

### Edge Examples

- Comments: query comments do not produce OR tokens in join-condition CST.
- Strings: OR-like text inside query string literals must not report.
- Preprocessor: BSL preprocessor is irrelevant after query text extraction.
- Multiline: OR tokens may be on their own query-string line.
- Nested constructs: nested join conditions are checked independently.
- BSL/SDBL variants, if relevant: Russian `ИЛИ` and English `OR` are equivalent when parsed by SDBL CST.
