## Описание диагностики

Между символами комментария "//" и текстом комментария должен быть пробел.

Исключением из правила являются _**комментарии-аннотации**_, т.е. комментарии начинающиеся с определенной последовательности символов.

## Источники

* [Стандарт: Тексты модулей, пункт 7.3](https://its.1c.ru/db/v8std#content:456:hdoc)

<div class="doc-lang doc-lang-en" markdown="1">

## Description

Between comment symbols "//" and comment text has to be a space.

Exception from the rule is _**comments-annotations**_, comments starting with special symbols sequence.

## Standard And Product Decision

- Standard or product policy: line comments should have a space between `//` and comment text.
- Why this diagnostic exists: comments without the separating space are harder to read and violate the documented BSLLS formatting convention.
- Non-goals: reporting empty comments, configured annotation comments, comment-looking text inside string literals, or fully parsing commented-out BSL code.
- Keep/drop decision: keep as a cheap comment-style diagnostic; classify the small remaining BSLLS CodeRecognizer divergence instead of adding receiver-specific exceptions.

## Semantic Oracle

- Checked language fact: a real line comment begins with `//` and has non-empty text immediately after the slashes.
- Must diagnose when: comment text starts immediately after `//`, including strict-mode multi-slash comments with text and BSLLS-compatible query-pipe/commented-code cases.
- Must not diagnose when: the comment is empty, starts with whitespace after `//`, is a configured annotation such as `//@`, starts a commented region marker `//#Область`, is an internal suppression directive, or is recognized as a BSLLS-compatible commented-code skip.
- Diagnostic anchor token/range: from the `//` column to the end of the physical line.
- Quick-fix target, if any: insert one space after `//`.

## CST Or Domain Fact Model

- Parser/tree source: source-line comment-start facts from `DiagnosticDocumentContext.comment_starts`, with a narrow query-pipe fallback for BSLLS parity when a commented query literal confuses multiline string state.
- CST/domain object types: physical source line, detected comment start column, comment body prefix.
- Extracted attributes: line number, comment start column, comment text, full-line versus inline comment state, and small BSLLS-compatible skip categories.
- Parse-error behavior: BSL024 is line-oriented and may run when the module has parse errors; BSL001 owns syntax diagnostics.
- Textual/regex behavior, only if genuinely textual: allowed. This is a textual style rule over line comments; regexes are bounded to comment prefixes and skip categories.

## Examples

### Invalid Examples

1. `//Без пробела`
2. `////Текст с ошибкой`
3. `Перем1 = 7; //И это плохо`

### Valid Negative Twins

1. `// С пробелом`
2. `//`
3. `//@УстановитьОбработчик`

### Edge Examples

- Comments: `//#Область СлужебныйИнтерфейс` is skipped, while `//#КонецОбласти` is diagnosed like BSLLS.
- Strings: `Ссылка = "https://support.example/path";` is not a comment.
- Preprocessor: commented region start markers are treated as annotations for parity.
- Multiline: each physical comment line is checked independently; selected `//|` query-pipe lines may report even inside a commented query block.
- Nested constructs: full-line commented code is not parsed as code; only a bounded BSLLS-compatible skip taxonomy is used.
- BSL/SDBL variants, if relevant: query-pipe fallback is textual and does not parse SDBL.
