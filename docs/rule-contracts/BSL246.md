# BSL246 SetPermissionsForNewObjects Contract

## Rule Identity

- Code: BSL246
- BSLLS compatible name: SetPermissionsForNewObjects
- Public name/i18n key: SetPermissionsForNewObjects / BSL246
- Default message/i18n key: RULE_MESSAGES_RU["BSL246"]
- Description/i18n key: RULE_METADATA["BSL246"].description
- Severity: ERROR
- Parameters/defaults: BSLLS has `namesFullAccessRole` with default `FullAccess,ПолныеПрава`; onec currently supports the same default role names without a public per-rule parameter surface.
- Rule status: parity-classified

## Standard And Product Decision

- Standard or product policy: only the full-access role should have the metadata flag that sets permissions for new objects.
- Why this diagnostic exists: a non-full-access role with this flag can silently accumulate rights to every object added after the role, creating excessive permissions for its users.
- Non-goals: do not diagnose full-access roles, roles without the flag, ordinary BSL modules, metadata files by themselves, or role XML when no managed application module is being checked.
- Keep/drop decision: keep as a BSLLS-compatible security/access-control diagnostic.

## Semantic Oracle

- Checked language fact: the current configuration contains at least one non-full-access role whose role XML has `<SetForNewObjects>true</SetForNewObjects>`.
- Must diagnose when: the checked file is `Ext/ManagedApplicationModule.bsl` under a configuration root and any role except `FullAccess` or `ПолныеПрава` has `SetForNewObjects=true`.
- Must not diagnose when: the checked file is not the managed application module, no configuration root exists, the only flagged roles are `FullAccess` or `ПолныеПрава`, all non-full-access roles have `SetForNewObjects=false` or no flag, or the Roles directory is absent.
- Diagnostic anchor token/range: owner range of the managed application module, line 1 from column 0 through the first line text.
- Quick-fix target, if any: disable the flag for the non-full-access role or rename/configure the role as an allowed full-access role where project policy permits it.

## CST Or Domain Fact Model

- Parser/tree source: Designer/EDT `Roles/*.xml`, configuration root lookup, and current BSL module path.
- CST/domain object types: current managed application module file, role XML file records.
- Extracted attributes: configuration root, module path suffix, role name from XML filename, `SetForNewObjects` boolean value, default full-access role allowlist.
- Parse-error behavior: BSL parse errors in the managed application module do not affect the metadata-level diagnostic; missing module range falls back to the first-line owner range.
- Textual/regex behavior, only if genuinely textual: XML tag extraction uses the existing compact XML helper for `<SetForNewObjects>true|false</SetForNewObjects>`.

## Examples

### Invalid Examples

1. Role `Users` has `<SetForNewObjects>true</SetForNewObjects>` and `Ext/ManagedApplicationModule.bsl` is checked.
2. Role `Managers` has the flag set to true while `FullAccess` exists separately.
3. Multiple non-full-access roles have the flag set to true.

### Valid Negative Twins

1. Role `FullAccess` has `<SetForNewObjects>true</SetForNewObjects>`.
2. Role `ПолныеПрава` has `<SetForNewObjects>true</SetForNewObjects>`.
3. Role `Users` has `<SetForNewObjects>false</SetForNewObjects>`.
4. A non-managed module is checked in the same configuration.

### Edge Examples

- Comments: XML comments are not semantic role facts unless the compact XML helper sees a real tag.
- Strings: BSL strings are irrelevant.
- Preprocessor: BSL preprocessor is irrelevant.
- Multiline: role XML may contain whitespace around the boolean value.
- Nested constructs: not relevant.
- BSL/SDBL variants, if relevant: SDBL is not relevant.
