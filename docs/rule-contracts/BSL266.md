- Rule status: verified

## Standard And Product Decision

- Standard or product policy: event handlers should set the cancel parameter only to cancel execution, not reset it to a non-cancel value.
- Why this diagnostic exists: assigning `Отказ`/`Cancel` to anything other than `Истина`/`True` or an accumulated cancel expression can accidentally clear a cancellation requested by another check.
- Non-goals: reporting reads of the cancel parameter, assignments to unrelated parameters, or validating event-handler names.
- Keep/drop decision: keep as a BSLLS-compatible event-correctness diagnostic.

## Semantic Oracle

- Checked language fact: a method parameter named `Отказ` or `Cancel` is assigned in the method body to a value other than true or an accumulated self-OR expression.
- Must diagnose when: the assignment left side is the cancel parameter in the method body and the right side is not `Истина`/`True` and not an expression containing both the cancel parameter and `Или`/`Or`.
- Must not diagnose when: the method has no `Отказ`/`Cancel` parameter, another variable is assigned, the apparent assignment is a default value in the method signature, the assignment is `Отказ = Истина`, the assignment is `Cancel = True`, or the assignment accumulates through `Отказ Или ...` / `Cancel Or ...`.
- Diagnostic anchor token/range: the full assignment line from the cancel parameter identifier to the line end.
- Quick-fix target, if any: replace reset-style assignment with `Истина`/`True` or preserve accumulated cancellation through `Отказ = Отказ Или ...`.

## CST Or Domain Fact Model

- Parser/tree source: `ProcInfo` parameter facts and bounded method-body assignment lines.
- CST/domain object types: procedure/function declarations, parameter identifiers, body assignment lvalue occurrences.
- Extracted attributes: method parameter names, cancel parameter case-insensitive match, full signature end line, assignment left-side name/range, and right-side expression text.
- Parse-error behavior: only parsed method facts are checked; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: current implementation uses a bounded line-level assignment-lvalue regex inside parsed method bodies; it must not scan outside method bodies or parameter lists.

## Examples

### Invalid Examples

1. `Процедура ПередЗаписью(Отказ)` with `Отказ = Ложь;`.
2. `Процедура ПередЗаписью(Отказ)` with `Отказ = Проверить();`.
3. `Procedure BeforeWrite(Cancel)` with `Cancel = False;`.

### Valid Negative Twins

1. `Отказ = Истина;`.
2. `Отказ = Отказ Или Не Проверить();`.
3. A method without an `Отказ`/`Cancel` parameter assigns another variable.

### Edge Examples

- Comments: inline comments after the assignment do not change the right-side value.
- Strings: string contents are not lvalue positions.
- Preprocessor: parsed method-body lines are checked the same way.
- Multiline: multiline signatures are skipped before body scanning; only single-line assignment facts are currently handled by the bounded lvalue scanner.
- Nested constructs: assignments inside nested blocks of the same method body count.
- BSL/SDBL variants, if relevant: SDBL is not relevant.

## Implementation Decision

- Change target: BSL266 body start selection, synthetic coverage, contract, and audit state.
- Delta category fixed by this change: onec-only false positives from scanning multiline signature default values as method-body assignments.
- Why not another layer: `ProcInfo` already exposes the full parameter-list end line needed to start the bounded body scan correctly.
- Rollback signal: `Отказ = Ложь` in the body stops reporting, signature defaults report, `Отказ = Истина` reports, self-OR accumulation reports, assignment character loses indentation, or contract validation fails.
