## Standard And Product Decision

- Standard or product policy: double negative boolean expressions should be rewritten to state the condition directly.
- Why this diagnostic exists: double negatives increase cognitive load and can lead to inverted-condition mistakes.
- Non-goals: single negation, negation text inside comments/strings, unrelated inequality without unary `Не`/`Not`, and syntax-error ownership.
- Keep/drop decision: keep as a BSLLS-compatible brain-overload/badpractice diagnostic.

## Semantic Oracle

- Checked language fact: a boolean expression contains a double negative pattern.
- Must diagnose when: a clean CST contains `Не Не <expr>` / `Not Not <expr>` or `Не <expr> <> <expr>` patterns compatible with BSLLS DoubleNegatives.
- Must not diagnose when: there is only one unary negation, the text is in comments/strings, the expression is a logical expression excluded by BSLLS-compatible behavior, or parse errors own the code.
- Diagnostic anchor token/range: from the outer `Не`/`Not` operator through the operand/comparison side that completes the double-negative expression.
- Quick-fix target, if any: remove the double negation or rewrite `Не X <> Y` to the direct equivalent.

- Parser/tree source: tree-sitter BSL CST.

- Parse-error behavior: invalid CST should not produce BSL060 facts; BSL001 owns malformed syntax.
- Textual/regex behavior, only if genuinely textual: none for valid CST paths.

### Invalid Examples

1. `Если НЕ НЕ Флаг Тогда`

### Valid Negative Twins

1. `Если НЕ Флаг Тогда`
2. `Если Флаг Тогда`
