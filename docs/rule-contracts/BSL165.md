## Standard And Product Decision

- Standard or product policy: global common modules should be named so their global visibility is visible from the module name.
- Why this diagnostic exists: global common modules add globally accessible procedures/functions; names without a global marker hide an important scope property.
- Non-goals: non-global common modules, missing/unreadable XML, client/global-client details covered by BSL166, and other naming predicates.
- Keep/drop decision: keep as a BSLLS-compatible common-module naming diagnostic.

## Semantic Oracle

- Checked language fact: a common module is global and its metadata name does not contain a global marker.
- Must diagnose when: sibling common-module XML exists, `Global` is true, and the module name does not contain `Глобальный` or `Global`.
- Must not diagnose when: XML is missing/unreadable, the module is not global, or the name already contains an accepted global marker.
- Diagnostic anchor token/range: the first non-empty/non-BOM line of the module file.
- Quick-fix target, if any: rename the common module to include an accepted global marker.

## CST Or Domain Fact Model

- Parser/tree source: XML metadata for common-module flags/name; BSL text is used for the diagnostic anchor.
- CST/domain object types: common-module XML snapshot and first non-empty module line.
- Extracted attributes: module name, `Global` flag, and anchor line range.
- Parse-error behavior: BSL parse errors do not affect this XML-driven naming rule.
- Textual/regex behavior, only if genuinely textual: XML tags and module-name token matching are textual metadata conventions.

## Examples

### Invalid Examples

1. Global common module named `ОбменДанными`.
2. Global common module named `Utilities`.
3. Global common module whose name contains no `Глобальный` or `Global` marker.

### Valid Negative Twins

1. Global common module named `ОбменДаннымиГлобальный`.
2. Global common module named `GlobalUtilities`.
3. Non-global common module without a global marker.

### Edge Examples

- Comments: comments may be the diagnostic anchor when they are the first real module line.
- Strings: BSL strings do not affect XML naming.
- Preprocessor: not a separate semantic target for this rule.
- Multiline: XML formatting may be multiline; tag extraction is fixed-tag based.
- Nested constructs: BSL procedures/functions do not affect this rule.
- BSL/SDBL variants, if relevant: SDBL is not relevant.
