## Описание диагностики

В модуле формы можно объявлять экспортные методы, доступные в клиентском контексте (обычно это методы-обработчики событий оповещения формы).
У экспортных методов формы может быть указана только директива компиляции `НаКлиенте`, так как для остальных практического смысла нет: обращение к методам формы извне доступно только после вызова метода `ПолучитьФорму`, который доступен только на клиенте.

Указание экспортному методу формы иной директивы компиляции либо ее опускание считается ошибкой.

*В некоторых версиях платформы 1С:Предприятие существовала ошибка, позволяющая использовать экспортные серверные методы форм, но проектировать прикладное решение с эксплуатированием ошибок платформы недопустимо.*

## Примеры

Неправильное применение экспортных методов в форме

```bsl
Процедура БезДирективКомпиляции() Экспорт
  // процедура доступна на сервере
КонецПроцедуры

&НаСервереБезКонтекста
Процедура НаСервереБезКонтекста() Экспорт
КонецПроцедуры

&НаСервере
Процедура НаСервере() Экспорт
КонецПроцедуры
```

## Description

In a form module, you can declare export methods that are available in the client context (usually, these are form notification event handlers). For export methods of the form, only the compilation directive `AtClient` can be specified, since for the rest there is no practical sense: accessing form methods from outside is available only after calling the method `GetForm`, which is available only on the client.

Specifying a different compilation directive for the export method or its absence is considered an error.

*In some versions of the 1C:Enterprise platform, there was an error that allowed using export server-side methods of forms, but it is unacceptable to design a solution using undocumented platform capabilities.*

## Examples

Incorrect use of export methods on a form

```bsl
Procedure One() Export
  // procedure without directive is available on the server
EndProcedure

&AtServerNoContext
Procedure AtServerNoContext() Export
EndProcedure

&AtServer
Procedure AtServer() Export
EndProcedure
```

## Standard And Product Decision

- Standard or product policy: exported form-module methods callable from the client must not be server-side methods unless explicitly client compiled.
- Why this diagnostic exists: exported server-side methods in managed form modules create incorrect UI/runtime contracts.
- Non-goals: ordinary forms, non-form modules, split-form generated layout modules, split method fragments, client-export methods, and form-like paths without metadata.
- Keep/drop decision: keep as a BSLLS-compatible managed-form correctness diagnostic.

## Semantic Oracle

- Checked language fact: a managed form module method is exported and its compiler directive is absent or not `&НаКлиенте` / `&AtClient`.
- Must diagnose when: the checked file is a full managed form module backed by `Form.xml`, the form is not ordinary, and an exported procedure/function is server/no-directive/both-context rather than client-only.
- Must not diagnose when: the form XML is missing, ordinary, `UseManagedForm=false`, split layout uses `Module.header`, the file is a split method fragment, or the exported method is client compiled.
- Diagnostic anchor token/range: exported method name range.
- Quick-fix target, if any: add/move the method to a client-side exported wrapper or remove `Экспорт` where not needed.

## CST Or Domain Fact Model

- Parser/tree source: current module procedure/function model plus nearby/current form metadata XML.
- CST/domain object types: `ProcInfo`, compiler directive lines, form module path, `Form.xml`, split-layout marker `Module.header`.
- Extracted attributes: exported flag, procedure name range, procedure compiler execution context, form XML text, ordinary/managed flags, and split-module markers.
- Parse-error behavior: missing procedure facts means no method diagnostics; syntax errors remain owned by BSL001.
- Textual/regex behavior, only if genuinely textual: XML flags are read from structured metadata text; method facts come from the existing procedure model.
