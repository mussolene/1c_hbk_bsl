# BSL274 WrongDataPathForFormElements Contract

## Rule Identity

- Code: BSL274
- BSLLS compatible name: WrongDataPathForFormElements
- Public name/i18n key: WrongDataPathForFormElements / BSL274
- Default message/i18n key: RULE_MESSAGES_RU["BSL274"]
- Description/i18n key: RULE_METADATA["BSL274"].description
- Severity: ERROR
- Parameters/defaults: none; enabled by default in BSLLS and supported by exact selection here.
- Rule status: verified

## Standard And Product Decision

- Standard or product policy: form elements must be bound to valid form data paths; unresolved form item data paths are exported as `DataPath` values starting with `~`.
- Why this diagnostic exists: unresolved form data paths make form fields disappear or fail extended configuration checks.
- Non-goals: do not validate whether every ordinary data path resolves; do not diagnose non-form XML, non-form modules, or form XML without `DataPath` values beginning with `~`.
- Keep/drop decision: keep as a BSLLS-compatible critical form metadata diagnostic.

## Semantic Oracle

- Checked language fact: a parsed form metadata item has `DataPath` beginning with `~`.
- Must diagnose when: a form module belongs to a form whose `Form.xml` contains a form item with unresolved `DataPath`, or the managed application module is checked and the configuration contains a form without modules with such an item.
- Must not diagnose when: `DataPath` is absent, empty, or does not start with `~`; the current module is not a form module or managed application module; a form with its own module is being checked from the managed application module path.
- Diagnostic anchor token/range: BSLLS reports the current module selection range; this implementation anchors at the current module owner range.
- Quick-fix target, if any: repair or remove the unresolved form element data binding in the form XML/design surface.

## CST Or Domain Fact Model

- Parser/tree source: metadata XML files under the configuration root.
- CST/domain object types: current module path, current form XML path, managed application module path, form XML `DataPath` elements.
- Extracted attributes: whether module is a form module, whether module is `Ext/ManagedApplicationModule.bsl`, form XML path, existence of sibling form module, and `DataPath` text.
- Parse-error behavior: if XML cannot be read, produce no diagnostics.
- Textual/regex behavior, only if genuinely textual: simple XML tag extraction is currently used for `DataPath`; the semantic predicate is textual because the exported form metadata stores the unresolved marker in text.

## Examples

### Invalid Examples

1. A form module whose `Form.xml` contains `<DataPath>~Object.Description</DataPath>`.
2. A form module whose dynamic-list column has `<DataPath>~List.Description</DataPath>`.
3. Managed application module when a form without its own module contains an unresolved `DataPath`.

### Valid Negative Twins

1. A form module with `<DataPath>Object.Description</DataPath>`.
2. A form module with no `DataPath` elements.
3. Managed application module when the unresolved form has its own module.

### Edge Examples

- Comments: XML comments are not form item data paths.
- Strings: BSL string contents are irrelevant; the rule reads form XML.
- Preprocessor: BSL preprocessor is irrelevant.
- Multiline: `DataPath` text may include whitespace around the value; the stripped value controls the predicate.
- Nested constructs: nested form item XML is diagnosed the same way if the `DataPath` starts with `~`.
- BSL/SDBL variants, if relevant: not applicable.
