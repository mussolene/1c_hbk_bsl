## Описание диагностики

При написании запросов не следует использовать соединения с вложенными запросами. Следует соединять друг с другом только объекты метаданных или временные таблицы.

Если запрос содержит соединения с вложенными запросами, то это может привести к следующим негативным последствиям:

- Крайне медленное выполнение запроса при слабой загрузке серверного оборудования
- Нестабильная работа запроса. При некоторых условиях запрос может работать достаточно быстро, при других - очень медленно
- Значительная разница по времени выполнения запроса на разных СУБД
- Повышенная чувствительность запроса к актуальности и полноте статистик. Сразу после полного обновления статистик запрос может работать быстро, но через некоторое время опять замедлиться

## Примеры

Пример потенциально опасного запроса, использующего соединение с вложенным запросом:

```bsl
ВЫБРАТЬ *
ИЗ Документ.РеализацияТоваровУслуг
ЛЕВОЕ СОЕДИНЕНИЕ (
   ВЫБРАТЬ Измерение1 ИЗ РегистрСведений.Лимиты
   ГДЕ Поле В (&СписокЗначений)
   СГРУППИРОВАТЬ ПО
   Измерение1
) ПО Ссылка = Измерение1
```

## Description

When writing queries, you should not use subquery joins. Only metadata objects or temporary tables should be joined to each other.

If the query contains joins with subqueries, then this can lead to negative consequences:

- Very slow query execution with low load on server hardware
- Unstable work of the request. Sometimes the query can work fast enough, sometimes very slow
- Significant difference in query execution time for different DBMS
- Increased query sensitivity to the relevance and completeness of sql statistics. After a complete update of statistics, the query may work quickly, but after a while it will slow down

## Examples

An example of a potentially dangerous query using a subquery join:

```bsl
SELECT *
FROM Document.Sales
LEFT JOIN (
   SELECT Field1 ИЗ InformationRegister.Limits
   WHERE Field2 In (&List)
   GROUP BY
   Field1
) BY Refs = Field1
```

## Standard And Product Decision

- Standard or product policy: query joins should not use nested queries as joined data sources.
- Why this diagnostic exists: joining subqueries can make query plans slower and harder to optimize; the preferred form is usually a temporary table or direct source.
- Non-goals: do not diagnose a subquery used as the only `ИЗ/FROM` data source with no join.
- Keep/drop decision: keep as a BSLLS-compatible query performance diagnostic.

## Semantic Oracle

- Checked language fact: an SDBL data source participating in a join contains a nested query source.
- Must diagnose when: a `nested_query_source` is the joined data source, or the initial data source is a nested query and the same table source has join clauses.
- Must not diagnose when: a nested query source is used without any join clause.
- Diagnostic anchor token/range: the nested subquery source range, including its parentheses, mapped to BSL query-string coordinates.
- Quick-fix target, if any: extract the nested query to a temporary table or join direct metadata sources.

## CST Or Domain Fact Model

- Parser/tree source: unescaped SDBL tree-sitter CST from query text blocks.
- CST/domain object types: `QueryTextBlockInfo`, `table_source`, `join_clause`, `nested_query_source`.
- Extracted attributes: whether `nested_query_source` is inside `join_clause`, whether its containing `table_source` has a `join_clause`, and mapped BSL line/character range.
- Parse-error behavior: skip malformed query fragments that do not produce the relevant source nodes.
- Textual/regex behavior, only if genuinely textual: legacy regex fallback may remain only for environments without query block/SDBL facts; valid CST paths must be structural.

## Examples

### Invalid Examples

1. `ЛЕВОЕ СОЕДИНЕНИЕ (ВЫБРАТЬ ... ) КАК T`.
2. `(ВЫБРАТЬ ... ) КАК T ЛЕВОЕ СОЕДИНЕНИЕ Catalog.X КАК X`.
3. `LEFT JOIN (SELECT ... ) AS T`.

### Valid Negative Twins

1. `ИЗ (ВЫБРАТЬ ... ) КАК T` with no join.
2. `ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Тест КАК T`.
3. A query text string containing the word `СОЕДИНЕНИЕ` inside a literal.

### Edge Examples

- Comments: query comments do not produce data-source CST nodes.
- Strings: join-like text inside query string literals must not report.
- Preprocessor: BSL preprocessor is irrelevant after query text extraction.
- Multiline: join subquery ranges may span several query-string lines.
- Nested constructs: nested query data sources are diagnosed at the outer data-source range.
- BSL/SDBL variants, if relevant: Russian and English join syntax are equivalent when parsed by SDBL CST.
