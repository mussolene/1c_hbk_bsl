# Карта оптимизации и развития продукта

Состояние на 8 октября 2026 года. Область: расширение VS Code / Cursor,
сервер LSP, CLI, Python API, MCP и постоянный индекс.
Это план работ, а не перечень уже реализованных возможностей или обещание сроков.

## Цель и исходное состояние

Цель: точная и отзывчивая поддержка BSL без отдельной установки среды выполнения,
с одинаковой семантикой в редакторе, CLI и интеграциях. Превосходство над другими
решениями подтверждается одинаковыми сценариями, а не количеством функций.

Уже существуют DocumentSnapshot, BslTypeEngine, постоянный SymbolIndex,
инкрементальный индексатор, наблюдение за файлами, адаптивная задержка диагностик,
проверки контрактов и инструменты профилирования. Их нужно расширять по результатам
измерений. Наличие механизма не доказывает его полноту или отсутствие ошибок.

Релиз 0.8.51 опубликован. Исправления 12 правил находятся в main и не входят в него.
Аудит по BSLLS 1.0.7 остается исходной точкой; каталог 1.1.0-rc.6 содержит 189 правил,
локальный каталог содержит 180, совпадают 178 названий. Отсутствуют 11 правил,
два локальных имени устарели относительно BSLLS. Совпадение имен не доказывает
совпадение семантики. Подробности предыдущего сравнения: [аудит](bslls-audit.md).

## Совместимость как условие каждой доработки

Источники контрактов: [публичные интерфейсы](public-surface.md),
[расширение](extension.md), [правила](diagnostic-rules.md), существующие тесты,
манифест расширения и проверка релизных артефактов. Не создавать второй каталог
контрактов. Заявление о поддержке среды требует текущей проверки в этой среде.

| Поверхность | Что сохранять и проверять |
|---|---|
| CLI и Python API | Команды, аргументы, импорты, формы результатов, коды завершения, stdout/stderr |
| Диагностики | Стабильные BSL-коды, имена-синонимы, подавления, select/ignore, параметры; изменения поведения документировать |
| Конфигурация | TOML, pyproject.toml, `.bsl-language-server.json`, приоритеты и предупреждения; не заявлять полную совместимость JSON |
| LSP | Согласованные capabilities, URI, кодировки позиций, версии документов, push/pull diagnostics, отмена запросов |
| MCP и CI | Схемы инструментов и ошибок, JSON/SARIF, режимы запуска и ограничения рабочей области |
| Индекс | Версия схемы, обновление и восстановление производного кэша, режимы off/symbols/full, исключения и лимиты |
| Расширение | Идентификаторы команд и настроек, встроенный сервер, пользовательский serverPath и действующий порядок выбора сервера |
| Среды | Четыре выпускаемые платформы; VS Code, Cursor, несколько корней, Remote SSH, Dev Containers и Docker проверять отдельно |

Для каждой реализации: ограниченный контракт, проверяемое изменение, текущие
результаты до/после, проверка связанного поведения и описание изменения в релизе.
Исправление подтвержденной ошибки диагностики допустимо, но не маскируется под
чистую оптимизацию. Исправления семантики и ускорение измерять отдельными шагами.

Внутренние структуры можно менять без сохранения двух реализаций. Новый путь должен
покрывать весь поддерживаемый контракт. Не добавлять скрытое переключение на старую
реализацию. Откат выполняется выпуском предыдущего проверенного артефакта; до
изменения формата кэша проверить поведение при возврате к прежней версии.

## Измерения и целевые показатели

Сначала PERF-01 устанавливает исходные значения и точный состав наборов. Числа ниже
являются предлагаемыми целями для прогретого сервера на зафиксированной машине,
а не текущими результатами. Время ожидания перед диагностикой включается в итог.

| Сценарий | Предлагаемая цель | Условие |
|---|---|---|
| Completion, hover | p95 <= 100 мс | Файл 1000 строк, индекс готов, фоновый анализ включен |
| Definition, references | p95 <= 200 мс | Фиксированный проект, одинаковая полнота результатов |
| Диагностики после последнего ввода | p95 <= 500 мс | Файл 1000 строк, одинаковый набор правил и контекст |
| Старая версия документа | 0 устаревших публикаций | Серии изменений, сохранение, закрытие, отмена |
| Длительная работа | Нет устойчивого роста ресурсов после прогрева | Прогон 60 минут, повторяемые циклы и ограниченные кэши |
| Оптимизация | Нет ухудшения точности; бюджет регрессии фиксируется до изменения | Сравнение на одной машине и одинаковом корпусе |

Разделять холодный запуск, первое открытие, прогретые запросы, переиндексацию и
большие файлы. Наборы: синтетические 100/500/1000/5000 строк, публичные примеры,
проект с метаданными и формами, несколько корней. Для реального проекта сохранять
только разрешенные агрегаты; исходники и абсолютные пути не публиковать.

Записывать commit, версию Python и парсера, ОС/CPU, параметры, размер корпуса,
число правил, число повторов, p50/p95, время CPU, память, очередь, отмены,
повторные разборы и обращения к SQLite. Отдельно учитывать время клиента,
транспорта, ожидания, разбора, семантики, правил и выдачи результата.

Переиспользовать scripts/bench_observability.py, bench_compare.py,
bench_profile.py, bench_per_rule.py, bench_timing.py и lsp_soak_profile.py.
В lsp_soak_profile.py режим по умолчанию вызывает обработчики напрямую;
`--transport` измеряет отдельный процесс по stdio на синтетическом документе,
с правилом BSL001 и индексом off. Он не заменяет замер всех правил или VS Code.
В CI проверять детерминированные счетчики; временные пороги применять
на стабильном исполнителе с достаточным числом повторов и учетом разброса.

## Когда оправдан C или Rust

Скорее да для отдельного вычислительного ядра, только после профилирования.
Tree-sitter и SQLite уже исполняют существенную часть работы нативно. Перенос
ожидания, лишних обходов, SQL или неверной инвалидации в другой язык сам по себе
не устраняет причину задержки. Выбор языка сейчас не фиксируется.

Условия допуска PERF-05:

1. Подтверждено узкое место CPU, остающееся после сокращения лишней работы.
   Известна его доля в полной задержке, включая ожидаемое ограничение по закону Амдала.
2. Выбран один ограниченный участок с чистым пакетным входом/выходом. Нет передачи
   каждого узла дерева через языковую границу и зависимости от внутренних Python-объектов.
3. Зафиксированы стоимость преобразований, владение памятью, ошибки, отмена,
   потокобезопасность и поведение без GIL там, где это применимо.
4. Предлагаемый порог принятия: ускорение участка >= 2 раз и полного целевого
   сценария >= 20% без ухудшения p95 и без роста пиковой памяти более 10%.
   Порог фиксируется до эксперимента; результат ниже порога означает отказ от переноса.
5. Существующие контракты и сравнительные примеры эквивалентны; ABI и версии
   зависимостей контролируются, все четыре платформы собираются и проверяются.
6. Если модуль нужен PyPI, доступны подходящие wheels и проверенная политика
   поддерживаемых Python/ОС. Установка не требует незаявленного компилятора.
   VSIX по-прежнему содержит готовый сервер.

Python остается владельцем протоколов и интеграций, если измерения не требуют
иного. Выбор между расширением CPython и отдельным процессом производится по
стоимости границы и изоляции отказа. Не добавлять постоянный второй сервер или
скрытый Python fallback. До полного покрытия контракта эксперимент не становится
основным путем. При неудаче удалить эксперимент, не оставлять две архитектуры.

зафиксировать конкретные примеры, размер корпуса, затронутые контракты и измерение
до реализации; после нее сохранить результаты, независимую проверку по риску,
обзор утечек и контрольную точку OACS. Закрытие требует фактических результатов,
а не только наличия кода. Новые регрессии возвращают задачу в работу.

В частной выборке 100 модулей, 3296 строк, 224808 байт. До и после текущих
изменений совпали все 525 диагностик, включая диапазоны и содержимое результатов.
Это проверка текстового анализа без исходного контекста метаданных. Выборка
содержит преимущественно небольшие модули и не представляет весь большой проект.
Исходники, манифест соответствия имен и сырые отчеты находятся вне Git.

На специальном synthetic входе с повторяющимся известным ошибочным именем
сбор кандидатов занимал около 74 мс на 1000 строк до изменения и около 2.1 мс
после. На 5000 строк после изменения около 11 мс, прежде секунды.
Это локальная проверка квадратичного алгоритма, а не заявление об ускорении
всего продукта в столько же раз. В независимом сравнении прежнего и нового
алгоритмов совпали 4387 кандидатов на 250 смешанных synthetic документах.

3.59 мс и hover 3.63 мс. После серии из 10 правок диагностический маркер
последнего состояния появился через 95.73 мс. Это время API VS Code, не отрисовки;
API диагностик не сообщает версию публикации, поэтому последняя версия проверена
уникальной позицией маркера. Релизный бинарник и source main имеют разную упаковку,
их времена запуска нельзя выдавать за эффект текущей оптимизации.

Docker Engine и существующий контейнер 1c-develop доступны. GUI эксперимент
в нем остановлен на недостающих NSS/NSPR библиотеках; системная среда не менялась.
Для текущей проверки использован установленный VS Code с отдельными профилем,
каталогом расширений и индексом. Контейнерная GUI поддержка пока не подтверждена.

Уточнена документация минимальной версии редактора: манифест текущего расширения
