- Rule status: verified

## Standard And Product Decision

- Standard or product policy: module code should be grouped into module regions.
- Why this diagnostic exists: methods, module variables, and executable module-level code outside `#Область` reduce navigation quality and violate the common 1C module-structure convention.
- Non-goals: unknown snippet files, split method fragments next to a canonical module file, ordinary-form `Forms/.../Ext/Module.bsl` compatibility files outside the BSLLS BSL156 module-type scope, comments, preprocessor directives, compiler directives by themselves, and syntax-error ownership.
- Keep/drop decision: keep as a BSLLS-compatible module-structure style diagnostic.

## Semantic Oracle

- Checked language fact: a known 1C module type contains a procedure/function, module variable declaration, or executable module-level code that is not fully inside any region.
- Must diagnose when: a supported module path has no regions and contains module variables, module-level executable code, or a procedure/function; or it has regions and such code is outside every region.
- Must not diagnose when: the path is not a BSLLS-supported module type for this rule, the file is a split method fragment next to a canonical module, the checked construct is fully inside a region, the line is only a comment/preprocessor/compiler directive, or the construct is a `ВызватьИсключение`/`Raise` statement ignored by the current BSLLS-compatible policy.
- Diagnostic anchor token/range: module variable declaration range, procedure/function name range, or executable module-level line range. For keyword-only multiline `Перем`/`Var` blocks, include directly attached compiler directives and the grouped declaration list.
- Quick-fix target, if any: wrap the code in an appropriate module-level `#Область`.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter BSL CST for procedure/function facts plus line-domain region and module-level statement facts.
- CST/domain object types: `ProcInfo`, region intervals from `#Область`/`#КонецОбласти`, module variable lines, executable module statement lines, and path-derived module kind.
- Extracted attributes: module path kind, split-fragment status, region intervals, procedure/function start/end/name range, module variable declaration range, and executable module-level line range.
- Parse-error behavior: use available procedure/region facts; `BSL001` owns syntax errors.
- Textual/regex behavior, only if genuinely textual: module path classification and line-level region/directive/variable filtering are textual because BSLLS scope and region style are path/line conventions.

## Examples

### Invalid Examples

1. Common module with `Процедура П() Экспорт` and no surrounding region.
2. Known object module with `Перем Глоб;` after `#КонецОбласти`.
3. Form module with module-level executable assignment outside all regions.

### Valid Negative Twins

1. Procedure fully wrapped by `#Область ... #КонецОбласти`.
2. Split method fragment file next to a canonical `Module.bsl`.
3. Ordinary-form compatibility path `Forms/.../Ext/Module.bsl` outside the BSLLS BSL156 scope.

### Edge Examples

- Comments: ignored unless they are inside a grouped module-variable range produced by a keyword-only declaration list.
- Strings: strings do not create module-level facts by themselves.
- Preprocessor: region directives define intervals; other preprocessor lines are not reported by themselves.
- Multiline: keyword-only `Перем`/`Var` declaration lists use a grouped range.
- Nested constructs: procedures/functions must be fully covered by a region interval.
- BSL/SDBL variants, if relevant: SDBL is not relevant.

## Implementation Decision

- Change target: BSL156 path scope, module-variable range extraction, contract, audit state, and tests.
- Delta category fixed by this change: semantic scope deltas for `CommonCommands/.../CommandModule.bsl` and ordinary-form `Forms/.../Ext/Module.bsl`; partial range deltas for keyword-only multiline module variable lists.
- Why not another layer: the rule is fundamentally line/path/region-structure based; existing procedure and region facts are sufficient, and modeling every BSLLS internal block range would add complexity without improving diagnostic signal.
- Rollback signal: ordinary-form compatibility modules report, common command modules stop reporting, procedures inside regions report, split method fragments report, or contract validation fails.
