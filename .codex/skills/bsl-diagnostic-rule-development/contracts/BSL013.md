# BSL013 Contract

## Rule Identity

- Code: BSL013
- BSLLS compatible name: CommentedCode
- Public name/i18n key: BSL013 / CommentedCode
- Default message/i18n key: get_rule("BSL013").message
- Description/i18n key: RULE_METADATA["BSL013"].description
- Severity: WARNING
- Parameters/defaults: none
- Rule status: contracted

## Standard And Product Decision

- Standard or product policy: Dead code should be deleted instead of kept as commented source.
- Why this diagnostic exists: It prevents stale code fragments from hiding real behavior and misleading maintainers.
- Non-goals: Normal prose comments, examples explicitly marked as examples, and query comments that are not BSL code.
- Keep/drop decision: keep

## Semantic Oracle

- Checked language fact: A comment group or inline comment looks like disabled executable BSL/query code.
- Must diagnose when: A comment group contains code-like syntax or an inline comment contains an assignment-like code fragment. Adjacent commented annotations/directives are included in the diagnostic range only when the group also contains executable code-like syntax.
- Must not diagnose when: The comment is prose, marked as an example, or does not contain executable-code structure.
- Diagnostic anchor token/range: the comment group range or inline comment range.
- Quick-fix target, if any: delete the commented code manually.

## CST Or Domain Fact Model

- Parser/tree source: `DocumentSnapshot.commented_code_facts`.
- CST/domain object types: comment line group, inline comment segment, code-like lexical markers.
- Extracted attributes: group start/end lines, comment start column, line end column, example marker state, and code-like marker state.
- Parse-error behavior: textual comment scan can run without valid CST; `BSL001` owns syntax errors.
- Textual/regex behavior, only if genuinely textual: this rule is intentionally textual because comments are not executable CST nodes.

## Examples

### Invalid Examples

1. A block of `// Если ... Тогда` code lines.
2. A comment group containing a method call with BSL syntax.
3. An inline comment that contains an assignment-like disabled statement.
4. A commented BSL annotation adjacent to a commented method body.

### Valid Negative Twins

1. A prose comment explaining business behavior.
2. A comment explicitly marked as an example.
3. A comment that mentions keywords without executable structure.
4. A standalone commented preprocessor directive block without executable code.

### Edge Examples

- Comments: comments are the target.
- Strings: string contents inside active code are not comment groups.
- Preprocessor: commented preprocessor-like prose is not enough by itself.
- Multiline: adjacent comment lines are grouped.
- Nested constructs: code-like nested comment groups are reported as one group.
- BSL/SDBL variants, if relevant: query-looking comment lines can be classified as commented code.

- Change target: BSL013 inline commented expression detection plus synthetic coverage and delta taxonomy for BSLLS-recognized vs intentionally ours-only comment-code categories.
