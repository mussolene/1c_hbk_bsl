# BSL148 AllFunctionPathMustHaveReturn Contract

## Rule Identity

- Code: BSL148
- BSLLS compatible name: AllFunctionPathMustHaveReturn
- Public name/i18n key: AllFunctionPathMustHaveReturn / BSL148
- Default message/i18n key: RULE_MESSAGES_RU["BSL148"]
- Description/i18n key: RULE_METADATA["BSL148"].description
- Severity: ERROR
- Parameters/defaults: `loopsExecutedAtLeastOnce=true`; BSLLS also exposes `ignoreMissingElseOnExit=false`, currently not exposed by onec.
- Rule status: parity-classified

## Standard And Product Decision

- Standard or product policy: every executable path in a function should end with an explicit `Возврат` / `Return` or exception before implicit function exit.
- Why this diagnostic exists: implicit `Возврат Неопределено` makes function contracts unpredictable and often hides incomplete branch handling.
- Non-goals: do not diagnose procedures; do not duplicate BSL032 on functions with no return statements at all; do not treat nested routine returns as outer function returns.
- Keep/drop decision: keep as a BSLLS-compatible function control-flow diagnostic, with stricter loop-exit semantics where BSLLS misses a real implicit exit.

## Semantic Oracle

- Checked language fact: a parsed function has at least one explicit return, but at least one control-flow path can reach function end without `Возврат` / `Return` or `ВызватьИсключение` / `Raise`.
- Must diagnose when: a function contains a return somewhere and an implicit exit remains reachable through missing `Иначе`, incomplete `ИначеЕсли`, incomplete `Попытка/Исключение`, a loop body that can continue without returning, or a skippable loop with no later return.
- Must not diagnose when: all top-level paths return or raise, the function has no returns and BSL032 owns it, the function subtree has parse errors, a nested routine contains the only return, or an endless `Пока Истина` blocks implicit exit.
- Diagnostic anchor token/range: function identifier token.
- Quick-fix target, if any: none; user must add the missing return/raise or rewrite control flow.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter function CST through `bsl148_function_name_spans`, called by `ModuleModel.validate_function_paths_return`.
- CST/domain object types: `function_definition`, `return_statement`, `rise_error_statement`, `if_statement`, `elseif_clause`, `else_clause`, `try_statement`, `while_statement`, `for_statement`, `for_each_statement`, `preprocessor`, and function identifier node.
- Extracted attributes: function identifier span, body children, branch bodies, try/except bodies, loop bodies, parse-error presence, and loop policy flag.
- Parse-error behavior: skip functions whose subtree contains `ERROR` or missing nodes; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: none; BSL148 is structural CST control-flow analysis.

## Examples

### Invalid Examples

1. Function with `Если ... Тогда Возврат ... ИначеЕсли ... Тогда Возврат ... КонецЕсли` and no final return.
2. Function with `Попытка Возврат ... Исключение Сообщить(...) КонецПопытки` and no later return.
3. Function whose terminal loop returns only from an inner conditional and has no return after the loop.

### Valid Negative Twins

1. Function where all `Если/ИначеЕсли/Иначе` branches return or raise.
2. Function with `Попытка/Исключение` followed by a top-level return after `КонецПопытки`.
3. Function with a terminal loop whose body itself always returns, under `loopsExecutedAtLeastOnce=true`.

### Edge Examples

- Comments: ignored by CST body walk.
- Strings: ignored by CST body walk.
- Preprocessor: preprocessor branches are treated like branch sets and require a complete else branch to be always-returning.
- Multiline: function identifier anchor comes from CST identifier span and header byte-to-LSP conversion.
- Nested constructs: nested function/procedure definitions do not contribute returns to the outer function.
- BSL/SDBL variants, if relevant: query text is irrelevant.

## Related-Rule Cluster

- Shared semantic object: function declaration and executable body control flow.
- Rules that may report on the same object/range: BSL032 reports functions with no return statements; BSL008 reports excessive returns; BSL051 reports unreachable code after terminal statements; BSL064 reports procedures returning values; BSL011/BSL019 may report complexity on the same function.
- Intended duplicate policy: BSL148 is suppressed by design when there are no returns, leaving BSL032 to report that simpler case. BSL051 may still report unreachable statements independently.

## Performance Contract

- Traversal/fact source: single tree-sitter function subtree traversal per function.
- Expected complexity: O(function CST size).
- Shared-pass reuse: currently local to BSL148; uses the same parsed tree as other structural diagnostics. Sequential statement reachability is scanned iteratively to avoid Python recursion depth limits on very long function bodies.
- Before/after measurement, if changed: no dedicated timing regression was needed; parity batch over 32,007 files completed under the same external harness. Later full-corpus diagnostics exposed a `RecursionError` in `implicit_exit_reachable`; converting the tail-recursive statement walk to an iterative loop preserved largest5 diagnostics total at 49265.

## Implementation Decision

- Change target: CFG helper `control_flow_rules.py`, BSL148 severity in `ModuleModel`, BSL148 tests, contract/audit, and iterative long-body reachability scanning.
- Delta category fixed by this change: semantic mismatch with BSLLS for `try_statement` followed by successor return; BSLLS-only terminal loop cases; severity mismatch with rule metadata.
- Why not another layer: rule semantics are structural and already owned by CST control-flow helpers; no regex/text layer is appropriate.
- Rollback signal: BSL148 targeted tests fail, BSLLS-only deltas reappear, BSL032/BSL051 overlap changes unexpectedly, or a sampled ours-only loop case proves semantically valid under all paths.
