# BSL154 CodeAfterAsyncCall Contract

## Rule Identity

- Code: BSL154
- BSLLS compatible name: CodeAfterAsyncCall
- Public name/i18n key: BSL154 / CodeAfterAsyncCall
- Default message/i18n key: RULE_MESSAGES_RU["BSL154"] and RULE_MESSAGES_RU_FMT["BSL154"]
- Description/i18n key: RULE_METADATA["BSL154"].description
- Severity: WARNING
- Parameters/defaults: none.
- Rule status: verified

## Standard And Product Decision

- Standard or product policy: code that follows asynchronous UI/platform calls may execute before the asynchronous result is available and should be reviewed.
- Why this diagnostic exists: continuing ordinary execution after a known asynchronous call is often a logic error; callers should return, break, or move continuation logic to the callback/notification handler.
- Non-goals: reporting common-module calls, object method calls with the same name, async calls with an immediate `Возврат`/`Return` or `Прервать`/`Break`, or asynchronous call lists outside the supported BSLLS-compatible set.
- Keep/drop decision: keep as a BSLLS-compatible async correctness diagnostic.

## Semantic Oracle

- Checked language fact: a supported module type contains a direct known asynchronous method call inside a procedure/function and ordinary code can execute after that call in the same control-flow chain.
- Must diagnose when: a form module, command module, or managed application module calls a known asynchronous global method and the containing statement or its parent block has a following statement other than immediate return/break.
- Must not diagnose when: the file type is outside the BSLLS-supported module set, the call is an object method call, there is no following executable statement, the following statement is `Возврат`/`Return` or `Прервать`/`Break`, or the syntax tree is invalid.
- Diagnostic anchor token/range: the full direct asynchronous global method call range.
- Quick-fix target, if any: return/break after the async call or move subsequent logic into the async completion handler.

## CST Or Domain Fact Model

- Parser/tree source: tree-sitter BSL CST.
- CST/domain object types: `method_call`, method-call `identifier`, `procedure_definition`, `function_definition`, and executable statement nodes such as `call_statement`, `assignment_statement`, `if_statement`, `while_statement`, `return_statement`, and `break_statement`.
- Extracted attributes: file/module path kind, direct method name, enclosing procedure/function, enclosing executable statement, next executable statement in the current or parent statement chain, and full direct method-call range.
- Parse-error behavior: invalid/missing CST produces no BSL154 facts; BSL001 owns syntax errors.
- Textual/regex behavior, only if genuinely textual: file path classification is textual because the BSLLS-compatible scope is module-kind/path based; semantic detection is CST-based.

## Examples

### Invalid Examples

1. Form module procedure calls `ПоказатьВопрос("?");` and then assigns `Результат = 1;`.
2. Command module loop calls `ShowQueryBox("?");` and then continues with another ordinary statement.
3. Async call inside an `Если` block is followed by ordinary code after the block.

### Valid Negative Twins

1. Async call followed immediately by `Возврат;`.
2. Async call followed immediately by `Break;` inside a loop.
3. Common module with the same async-looking call.

### Edge Examples

- Comments: commented method names do not create CST method calls.
- Strings: string literals do not create CST method calls.
- Preprocessor: not a separate semantic target for this rule.
- Multiline: multiline calls anchor on the full direct method-call range.
- Nested constructs: parent block follow-up statements count because execution can continue after the async call's enclosing statement.
- BSL/SDBL variants, if relevant: SDBL is not relevant.

## Implementation Decision

- Change target: BSL154 contract, parity classification, audit state, and verification evidence.
- Delta category fixed by this change: range-only mismatch fixed by reporting the full direct method call; object-method false positive guard made explicit after broadening the diagnostic range through string arguments.
- Why not another layer: CST already distinguishes direct statement calls from object calls through the `method_call` parent shape, and the enclosing statement chain is sufficient for this rule's supported flow model.
- Rollback signal: object method calls report, common modules report, return/break negatives report, direct async calls with following ordinary code stop reporting, or contract validation fails.
