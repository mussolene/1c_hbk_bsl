## Standard And Product Decision

- Standard or product policy: Source code must not contain hardcoded credentials or secret-like values.
- Why this diagnostic exists: It prevents accidental credential exposure and unsafe deployment practices.
- Non-goals: Comments, suppression-disabled lines, and ordinary non-secret string literals.
- Keep/drop decision: keep

## Semantic Oracle

- Checked language fact: A code line contains a secret-looking credential token or assignment.
- Must diagnose when: A non-comment code line matches the hardcoded credential pattern.
- Must not diagnose when: The same text is in a full-line comment, is suppressed, or does not match the credential taxonomy.
- Diagnostic anchor token/range: the matched credential token range.
- Quick-fix target, if any: none

## CST Or Domain Fact Model

- Parser/tree source: `DocumentSnapshot.hardcoded_credential_facts`.
- CST/domain object types: source line, masked/comment-aware lexical credential match.
- Extracted attributes: line index, matched token start, matched token end.
- Parse-error behavior: textual security scan can run without a valid CST; `BSL001` owns syntax errors.
- Textual/regex behavior, only if genuinely textual: credential detection is a textual/security rule and uses a credential pattern.

## Examples

### Invalid Examples

1. A code line assigns a password-like literal.
2. A code line assigns a token-like literal.
3. A code line assigns a secret-like literal.

### Valid Negative Twins

1. A full-line comment mentions a password word.
2. A normal string literal does not match secret taxonomy.
3. A suppressed line is excluded by suppression handling.

### Edge Examples

- Comments: full-line comments are skipped.
- Strings: string content is only reported when the code line matches credential taxonomy.
- Preprocessor: not a separate target.
- Multiline: each line is scanned independently.
- Nested constructs: not relevant.
- BSL/SDBL variants, if relevant: SDBL is not relevant.
